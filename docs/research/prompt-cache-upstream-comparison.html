Research report · safe follow-up applied

Prompt and token caching across VS Code Copilot, Copilot CLI, and github-router

A source-first comparison of provider-side prefix reuse, cache-control and breakpoints, prompt construction, session persistence, compaction, model gates, and observability.

Lookup date: 2026-09-01 Router baseline: commit 8253216, package 0.3.303; follow-up package 0.3.304 Conclusion: research complete; bounded, non-policy improvements applied
Headline: The clients implement caching at three different layers. VS Code has the clearest public request pipeline: rolling Anthropic breakpoints, model-gated Responses breakpoints, an optional Responses cache key, and a Cache Explorer fed by provider-reported usage. Copilot CLI's executable is closed, so its current request builder cannot be verified from the public CLI repository; its public SDK, documentation, changelog, and issues prove durable local session state and cache accounting, but not durable provider KV-cache state. github-router already has a more deliberate split than either a blanket marker policy or no policy: it preserves public caller controls, adds explicit caching only for discrete reusable-prefix Responses calls, and leaves growing conversations provider-managed after a measured regression. The remaining optimization work should be evidence-driven, catalog-aware, and conservative about rewriting history bytes.

1. What “caching” means here

Prefix hygiene

The client decides the exact order and bytes of tools, instructions, history, and the current turn. A change early in that rendered request can make later content ineligible for reuse.

client-controlled

Provider prompt cache

The model service reuses a matching prefix or a marked cache boundary. Cache markers and provider-facing keys are request controls, not local copies of model KV state.

provider-owned

Local session state

Transcripts, tool results, plans, checkpoints, model identifiers, and expiration hints can survive a restart. Reconstructing the prompt is not proof that the provider cache is warm.

persisted separately

The comparison below keeps these mechanisms separate. A lower latency measurement alone is not a cache hit. The strongest evidence is a provider-reported cached-token counter or billing signal, paired with a captured request showing the relevant transformation.

3. VS Code Copilot: the public implementation

3.1 Rolling breakpoints are an explicit prompt-shape strategy

cacheBreakpoints.ts defines MaxCacheBreakpoints = 4 and addCacheBreakpoints(messages, apiType). It first removes markers unsupported by the selected API, then scans from the newest messages backward. It prefers recent tool results, the current user content, and assistant messages without tool calls, with a fallback scan of leading system and user content.

  • For responses, assistant messages are not marked. Supported content includes text, image, document, and opaque input_text, input_image, and input_file blocks.
  • For other API types, assistant content can be marked and the accepted opaque types are the Chat/Anthropic-shaped variants.
  • The source comment explicitly says a new turn generally incurs a miss because prior content moves relative to the current user boundary, while an agentic tool loop can hit on the prior tool result.

This function prepares provider markers. It does not itself create or persist model state.

3.2 Anthropic Messages: four rolling markers, with a gated one-hour TTL

In messagesApi.ts, createMessagesRequestBody clears old marker fields, converts raw messages, and then calls:

  • addToolsAndSystemCacheControl: marks the last non-deferred tool and final system block.
  • addMessagesApiCacheControl: marks the last cacheable block in each of the two most recent cacheable messages.

The combined policy can use up to four { type: "ephemeral" } markers. The normal TTL is the provider default. An extended { type: "ephemeral", ttl: "1h" } is selected only when the model, experiment, location, and non-subagent gates pass. The source specifically excludes short-lived subagent calls from the extended TTL. The internal marker is CacheType = 'ephemeral'; the built-in Anthropic converter translates the internal cache_control data part, while a July 2026 fix makes unsupported BYOK providers fail closed rather than leaking the sentinel upstream.

Verified source The exact implementation does not claim that an Anthropic cache survives a process restart. It only controls the request markers and reads returned usage.

3.3 OpenAI Responses: explicit mode, optional key, and compaction

responsesApi.ts emits prompt_cache_options when the model supports the capability. The current capability helper modelSupportCacheBreakPoints returns true for the GPT-5.6 family. Depending on the experiment and marker support, the mode is explicit or implicit. Raw markers become prompt_cache_breakpoint: { mode: "explicit" } on the preceding supported content block.

When the cache-key experiment is enabled and a conversation ID exists, the body also receives:

body.prompt_cache_key = `${options.conversationId}:${endpoint.family}`

The same builder sends store: false. A cache key is therefore an association/control value, not evidence that provider KV state is stored in the local session or guaranteed to survive a restart.

Responses context management is separately requested at Math.floor(endpoint.modelMaxPromptTokens * 0.9), with a 50,000-token fallback. The returned encrypted compaction item and previous_response_id are round-tripped by the Responses converter. This is a provider/API continuation protocol, not the same thing as a local summary.

3.4 Prompt construction deliberately moves drift toward the tail

In agentPrompt.tsx, the first-turn customizations index is snapshotted and reused. If it changes, the live value is rendered as a drift block in the latest user message instead of rewriting the system prompt. The comment explicitly identifies this as protection for the system-prompt cache.

The Copilot CLI prompt adapter in copilotCLIPrompt.tsx puts the user request first, then conditionally appends reminder, attachment, edited-file context, and a repeated query tag. Its comment says frozen content should be used when available, but the shown resolver renders current request variables and edited-file events. Resource elements are gathered through Promise.all and appended into a shared array. The source excerpt does not establish a deterministic completion-order guarantee for multiple resources. This is a stability risk to validate, not proof that every live request is unstable.

3.5 Diagnostics and local persistence are separate from the provider cache

Cache Explorer is read-only. It compares adjacent recorded model turns, displays provider-reported inputTokens and cachedTokens, calculates a cache percentage, and diffs system, tools, request options, and messages to locate the first likely divergence. It does not change request bodies.

Agent Host persists only a small status slot under _meta["vscode.promptCache"]:

{
  modelId: string,
  cacheExpiresAt: string
}

The corresponding AgentHostPromptCache read/write seam stores and compares that metadata. Copilot transcripts are persisted separately as JSONL under extension storage. Neither source contains prompt bytes or provider KV tensors. Official Cache Explorer documentation says caches expire after inactivity, but does not state a contractual duration, eviction algorithm, cross-session guarantee, or universal provider rule.

4. Copilot CLI: what can and cannot be learned publicly

4.1 The executable request builder is not public

The public CLI repository currently exposes README.md, changelog.md, installer and workflow files, but no CLI source, tests, or request-construction module. The public Copilot SDK exposes a JSON-RPC session and request-interception layer, but its buildFetchRequest path reconstructs opaque body bytes. That proves the SDK bridge does not canonicalize an intercepted body; it does not reveal how the closed CLI creates those bytes.

4.2 Confirmed provider and session signals

  • CLI issue #4185 records Anthropic cache_control breakpoints and a historical five-marker failure when --add-dir was used. The v1.0.73 changelog records the associated Anthropic subagent fix. The issue also reports that GPT subagent requests did not carry that field. Current breakpoint placement and TTL are not visible in public CLI source.
  • CLI and SDK documentation describe local session state under ~/.copilot/session-state/{sessionId}/, including conversation history, tool results, plans, checkpoints, and session artifacts. Credentials and in-memory tool state are not persisted. Resuming a session rebuilds local context; it does not prove a warm provider cache.
  • The SDK protocol models cache-read/write usage, cache expiration, model ID, and usage checkpoints. These are durable accounting/status fields, not serialized provider KV state.
  • Official CLI context-management documentation describes automatic compaction at approximately 80% usage, a buffer near approximately 95%, summary replacement, and numbered checkpoints. It does not specify provider cache TTL or cross-process provider-cache reuse.

4.3 Important issue-reported serialization warning

Open issue #4500 reports that a BYOK OpenAI Responses completion-nudge path rebuilt the entire input array rather than replaying prior items byte-for-byte. The reporter measured cached tokens dropping from 114,688 to 5,632 on a 100K-token conversation. The report concerns CLI 1.0.79, has no linked fix or public request-builder source, and must not be presented as a current v1.0.83-0 defect without a fresh reproduction. It is nevertheless a high-value failure mode for any proxy that reparses and reserializes growing history.

Open issue #3808 requests explicit Anthropic breakpoints, configurable TTL, and cache-status reporting. Its open status is evidence that the public CLI contract does not yet document these controls, not proof that no internal implementation exists.

5.2 Why the growing-conversation exception is correct

applyResponsesCachePolicy explicitly excludes workload: "conversation". The repository records a controlled gpt-5.6-sol regression when only a roughly 2K-token stable system block was explicitly marked: warm turns read about 2K tokens while recomputing about 25K of accumulating history. A positivity check would have called that a pass, so the live probe instead uses per-warm-turn coverage:

(cache_read_input_tokens + cache_creation_input_tokens)
/ (input_tokens + cache_creation_input_tokens + cache_read_input_tokens)

The documented target is a 0.90 mean for strict Claude and GPT-5.6 trials. The measured comparison separates whole-growing-history reuse from a small static-prefix hit. This is a stronger standard than copying a marker strategy from another client without testing the Copilot backend.

5.3 Translation and serialization path

The shared assembleResponsesPayload maps both worker and Anthropic-shim traffic into one Responses shape. It puts dynamic instructions before the neutral message list, preserves assistant text/tool-call order, and invokes the cache policy only when the caller supplies one. The translated Claude main loop uses workload: "conversation", so it intentionally avoids the explicit GPT-5.6 policy.

responsesCacheKey hashes namespace, model, workload, optional scope, stable prefix, and tools. It deliberately excludes dynamic/user messages. This is a router-owned key convention, not evidence about Copilot's internal namespace. It also means endpoint, catalog revision, and backend identity are not part of the local digest. Whether those dimensions matter to Copilot should be tested before changing the key.

resolveModelInBody reparses and serializes only when model/translation/sanitization changes are needed. That is the right default for public passthrough: unconditional canonicalization would alter request bytes even when the caller already supplied a stable prefix. The remaining risk is any owned path that rebuilds unchanged history during a nudge, retry, or translation.

5.4 Usage and safety machinery

  • normalizeOpenAIUsage converts inclusive OpenAI input totals into disjoint uncached, cache-read, and cache-write buckets.
  • Native Anthropic usage keeps input_tokens, cache_read_input_tokens, and cache_creation_input_tokens distinct; the request log sums them when reporting total input.
  • The catalog exposes context, prompt, output, endpoint, reasoning, and billing token-price metadata. The worker catalog view intentionally exposes only ordinary input/output price observations; cache-price semantics remain unverified.
  • Worker context management is structural and send-time: it clones before pruning, preserves tool-call/result pairing, caps tool results, and uses a 128K fallback when catalog context metadata is absent. Worker agents do not attach Pi's durable JSONL session backend, so worker transcripts and cache statistics are not durable across worker restarts.

7. Safe follow-up applied, then prioritized next steps

Safe follow-up applied: the branch now uses the stricter valid max_prompt_tokens / max_context_window_tokens ceiling for worker input budgeting, logs positive provider-reported cache TTL observations on supported non-streaming OpenAI-shaped responses, and corrects the explicit GPT-5.6 wording to “reusable-prefix only.” Cache-price fields remain out of the model-facing catalog until their live semantics are verified. These changes do not add upstream request fields, broaden cache policy, or alter growing-conversation behavior. Package version is 0.3.304; focused tests (227 passes), typecheck, and lint passed.

Remaining items below are a research backlog, not an approval to change provider request behavior. Every request-shape change must follow the repository's compatibility-probe and matrix rules.

  1. Build a direct-versus-proxy cache evidence matrix before changing policy

    Run controlled cold/warm pairs for native Claude, GPT-5.6 Responses, GPT-5.5, Gemini Chat, and Grok Responses. For each model, test same-process turns, changed suffix, changed early prefix, changed tools, streaming/non-streaming where supported, process restart, and session resume. Capture client-to-router and router-to-Copilot bodies with credentials and user data redacted, plus model, endpoint, prompt-cache fields, usage counters, latency, and retry attempts.

    Acceptance: a warm read must be shown by a provider counter or billing signal. If a provider reports no cache fields, record INCONCLUSIVE, never PASS. The existing probe:cache is a strong base, but it does not identify the exact reused byte boundary and hidden pre-first-byte retries can contaminate a cold trial.

  2. Make explicit eligibility capability-driven where the live catalog supports it

    GPT56_EXPLICIT_CACHE_MODELS is currently a fixed ID set in prompt-cache.ts. First verify whether Copilot's live catalog exposes a reliable explicit-cache capability and endpoint constraint. If it does, derive the decision from that capability with a conservative fallback. If it does not, retain the allowlist but make additions probe-gated and visible in the compatibility matrix. Do not broaden to every Responses model based only on an OpenAI-compatible type shape.

  3. Preserve byte identity on replay paths, and instrument before canonicalizing

    Audit nudges, retries, translation, and any history reconstruction against the CLI #4500 failure mode. For unchanged public bodies, retain the raw bytes. For router-owned payloads, use deterministic construction and compare the overlap between adjacent requests after removing only moving cache-marker fields. Avoid globally sorting or reserializing caller-owned JSON until a probe demonstrates that the chosen canonical form improves warm coverage without breaking an existing provider cache chain.

  4. Complete cache economics and effectiveness for owned worker calls

    The remaining work is to retain cache_ttl_seconds in worker usage mapping and compute per-model cached fraction, effective input cost, and TTL observations in a bounded diagnostic artifact rather than stuffing them into every model-facing result. Keep malformed or absent provider fields explicitly unknown. Cache-price fields are not exposed in the model-facing catalog until their live semantics are verified.
