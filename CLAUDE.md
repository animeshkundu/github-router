# github-router

A reverse proxy that exposes GitHub Copilot as OpenAI and Anthropic compatible API endpoints.

## Primary deployment target

The primary deployment target for this project is **Windows 11**. macOS and Linux are supported and tested, but Windows is the canonical user environment — every PR must pass the `windows-latest` CI job before merge. A Windows CI failure is treated as a merge blocker, not as flake. If Windows behavior diverges from POSIX, the Windows path is the authoritative one to fix; do not POSIX-skip a Windows failure to land a change.

The canonical end-user setup is **Windows 11 + Claude Code (the CLI client) + a GitHub Copilot _Enterprise_ license**. The enterprise license is load-bearing for feature decisions: it unlocks catalog models gated `restricted_to: ["enterprise"]` and the 1M-context Opus variants — `claude-opus-5` (the spawned-Claude-Code default, stand_in's Opus row, and opus_critic's model; the single base slug already advertises `max_context_window_tokens: 1_000_000` — no `-1m` sibling needed). When choosing models or windows, assume the enterprise catalog is present (prefer the 1M variants), but always gate on the live catalog with a non-enterprise fallback so the proxy still works on lesser tiers.

## Review checklist (read before submitting / approving any PR)

- **Stream lifecycle**: every `controller.enqueue` / `controller.close` / `reader.read` call site must have a regression test that intentionally races consumer cancel against the call. Cooperative-mock tests are insufficient — they cannot reproduce the microsecond window where Bun's HTTP layer closes the controller while a `pull()` is mid-`await`. See `tests/integration/chaos.test.ts` for the test pattern.
- **The smoking gun**: a new `Could not deliver error event` warn-log is a bug, not a routine warning. Open an issue and treat as a regression.
- **Author responsibility**: PR descriptions must list the failure modes the author considered and tested, not just the happy path. Reviewers can only check what they're asked about — narrow prompts produce narrow reviews. The class of bug we missed in the manual `ReadableStream({pull})` rollout was an enqueue-after-cancel race that the catch block was clearly intended to handle, but no test ever reproduced it. The catch-handler's existence is not a substitute for an actual race-triggering test.
- **Spec ≠ runtime**: WHATWG/Anthropic spec compliance is necessary but not sufficient. Verify what Bun (and Node undici when relevant) actually throw at runtime. Don't reason "the spec says close is idempotent" — verify "Bun throws `TypeError: Invalid state: Controller is already closed` if you enqueue after close."
- **Bun request-signal quirk**: `c.req.raw.signal` from a Bun/srvx HTTP handler is aborted as soon as the request body is fully consumed (i.e., right after `await c.req.json()`), even when the consumer is still happily reading the response. Do NOT propagate it into upstream `fetch()` calls — every such call would fail immediately with "This operation was aborted." `/v1/responses` and `/mcp` both intentionally drop it; tear-down on consumer cancel is handled at the `ReadableStream.cancel()` callback for streaming responses, and is a no-op for non-streaming responses (the upstream call completes regardless). If a future change truly needs to propagate consumer cancel, verify with a real Bun.serve listener — unit tests with `app.request(new Request(...))` do not reproduce the quirk.
- **Compatibility probe rule**: every field, header, body shape, or tool type that any client (Claude Code, Codex, raw API users) emits MUST have a probe row in `scripts/probe-copilot-compat.sh` AND a row in `docs/copilot-compat-matrix.md` — with an explicit accept-or-reject expectation. Discovery sources: real traffic (`bun run discover:fields` after launching with `GH_ROUTER_LOG_FIELDS=1`), code changes that emit new shapes, exploratory probing. The probe set grows monotonically; removing a row requires written justification in the matrix doc. Run `bun run probe:copilot` (strict mode) before merging changes that touch request shaping. Symmetric: both `❌ 400` and `✅ 200` rows are asserted, so drift in either direction surfaces immediately rather than after users hit it.
- **Strip-rule probe rule**: adding (or removing) a strip rule in `stripAnthropicOnlyFields` / `sanitizeCacheControl` / equivalent requires (a) an end-to-end probe in `scripts/probe-copilot-compat.sh` asserting the user-facing behavior the strip enables (typically a `200` where without the strip Copilot would 400), AND (b) a row in `docs/copilot-compat-matrix.md` documenting the upstream truth. The probe id should be referenced in the strip's code comment so a future contributor following a breadcrumb lands on the empirical evidence.
- **Windows-first CI**: `windows-latest` CI must be green before merge. Any test that skips on `process.platform === "win32"` requires an explicit written justification (e.g., the symlink-confused-deputy probe at `tests/isolated/lib-paths.test.ts:108-115` is justified because file-typed symlinks legitimately require admin/Developer Mode). Adding new `win32 return` guards to existing tests is a regression of CI coverage on the primary deployment target.
- **Zero-tolerance for flaky / failing CI**: every PR must have a fully green CI run across the entire matrix before merge — no exceptions, no "rerun until green," no "the failing test is unrelated to my change." Flakes and pre-existing failures are merge blockers for whoever is next to land a PR, regardless of who introduced them. If you encounter a flaky test, root-cause it and either fix the underlying race / resource leak / timing bug, OR delete the test with a written justification in the PR description (suppressing via `.skip` or retry-loops is not acceptable — those convert visible bugs into invisible ones). The cost of pausing to fix a flake is bounded; the cost of a green-rate that creeps below 100% compounds into "CI doesn't mean anything" and bugs ship.
- **MCP tool surface minimality**: every input/output field of every MCP tool (the personas under `PERSONAS_READ`/`PERSONAS_WRITE` and the utility tools under `NON_PERSONA_MCP_TOOLS` in `src/lib/peer-mcp-personas.ts`) must be required to call the tool, model-tunable in a way that improves outcomes, OR directly actionable feedback the model can act on next call. Echoed inputs, diagnostic-only fields, and non-actionable failure metadata cost the model's context for no return. When adding or extending a tool, write "what would the model do with this?" for each proposed field; if the answer is "nothing," cut it. See [`docs/peer-mcp-design.md`](docs/peer-mcp-design.md) "Design principle: ruthlessly minimal MCP tool surface" for the worked example and the per-field rationale.
- **Version bump per PR**: every PR must include a `package.json` patch bump (`npm version patch --no-git-tag-version`, or hand-edit the `"version"` field). The release workflow loops `npm version patch` until it finds an unpublished value, then publishes the unscoped `github-router` package; the post-publish push of the bumped `package.json` back to master runs under `continue-on-error: true` and silently fails without `secrets.PAT`, so the repo-side version drifts behind npm. Bumping per PR keeps `package.json` honest, which keeps `github-router --version` and the startup banner honest, which makes crash reports actionable. The single source of truth for the running version is `getPackageVersion()` in `src/lib/version.ts` — it reads `package.json` at runtime (not build time) because release.yml builds BEFORE the bump loop, so a build-time inline would always ship the pre-bump value.

## Commands

```bash

bun run dev          # Dev server with hot reload
bun run lint:all     # Lint entire project
bun run typecheck    # TypeScript type checking (root config + browser-bridge config)
bun run test         # Run the FULL suite exactly as CI does (build + both lanes)
bun test             # Quick lane-1 sweep only; excludes tests/isolated/** (see below)
bun run start        # Production server (port 8787)
```

### Test lanes (why `bun run test` is not `bun test`)

The suite runs in two lanes, driven by `scripts/run-tests.ts` (the single source of
truth — CI invokes the same script, so local and CI can never drift):

1. every test except `tests/isolated/**`, in one process;
2. each `tests/isolated/*.test.ts` file in its OWN process.

The split is load-bearing. Files under `tests/isolated/` use `mock.module()`, which
bun applies process-globally and which `mock.restore()` cannot undo, so sharing a
process lets one file's mock corrupt another's. The worst case is a deadlock, not a
bad assertion: the `node:child_process` spawn mock in
`tests/isolated/lib-launch-child.test.ts` returns a fake child that never emits
`close`, and the spawn in `src/lib/code-search.ts` then awaits it forever — which is
exactly why a bare `bun test` used to hang with no summary.

`bunfig.toml` therefore excludes `tests/isolated/**` from discovery so a bare
`bun test` stays safe (it becomes lane 1 only). A CLI `--path-ignore-patterns`
OVERRIDES that bunfig value; that is how lane 2 opts the directory back in per file.
Consequence to know: running an isolated file directly with `bun test
tests/isolated/foo.test.ts` matches zero tests and exits 1 — pass
`--path-ignore-patterns node_modules/**` to override, or just use `bun run test`.

`bun test` does not build, so the two `dist/main.js` precondition tests
(`tests/internal-hooks-crash.test.ts`, `tests/node-compat.test.ts`) fail until you
run `bun run build`. `bun run test` builds first, so it is green from a fresh clone.

CI runs `bun scripts/ensure-ast-grep.ts` after the build and before this test runner.
It provisions `ast-grep` from the pinned toolbelt manifest and hard-fails when it
remains unavailable: the six `mode:"ast"` code-search tests otherwise skip rather
than exercise their assertions. This is a CI dependency check, not a substitute for
running `bun run test` locally.

`bun run typecheck` runs `tsc && tsc -p tsconfig.browser.json`: the root config and
the separately bundled Node native-messaging bridge (`src/browser-bridge/**`) are
both checked. `src/browser-ext/**` deliberately remains outside that command: it is
MV3 extension JavaScript with `chrome.*` service-worker globals and needs a third
configuration plus `@types/chrome`; adding that coverage remains follow-up work.

- `github-router debug [...]` — internal diagnostics; not for user-facing flows.

## Architecture

- **Stack**: TypeScript / Bun / Hono / SSE streaming
- **Import alias**: `~/` maps to `src/`
- **Token storage**: `~/.local/share/github-router/github_token`

### Two patterns

1. **Passthrough**: Forward directly to Copilot API:
   - `/v1/chat/completions`, `/v1/responses`, `/v1/embeddings`
   - Service: `src/services/copilot/create-*.ts` → handler → route

2. **Passthrough with sanitization**: Forward to Copilot, stripping unsupported fields:
   - `/v1/messages` (Anthropic) → strip `cache_control.scope` generally and the whole unsupported `cache_control` object from signed thinking blocks (signed fields remain exact), filter beta headers → Copilot `/v1/messages?beta=true`
   - `/v1/messages/count_tokens` → same sanitization → Copilot `/v1/messages/count_tokens?beta=true`

### Beta header filtering & stealth-vs-leverage

`github-router claude` defaults to **leverage** (extended-betas ON; 20 prefixes forwarded, `EXPLICITLY_STRIPPED_BETA_PREFIXES` deny-list catches anything Copilot 400s on); `start`/`codex` default to **VS Code stealth** (3 prefixes only). Body-level `budget`, `output_config.schema`, `betas`, and per-tool `eager_input_streaming` are stripped on `/v1/messages` and `/v1/messages/count_tokens`. Full allowlist + strip-list + opt-out flags in [`docs/beta-headers.md`](docs/beta-headers.md).

### Experimental Claude Code features auto-enabled

`github-router claude` auto-enables five `CLAUDE_CODE_*` env-var feature gates via a presence-based guard (any user-set value is preserved — set to `0`/`false`/`off` to opt out per-feature): `CLAUDE_CODE_ENABLE_EXPERIMENTAL_ADVISOR_TOOL`, `CLAUDE_CODE_FORK_SUBAGENT`, `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`, `CLAUDE_CODE_ENABLE_FINE_GRAINED_TOOL_STREAMING`, `CLAUDE_CODE_ENABLE_TASKS`. **Note**: FORK_SUBAGENT silently no-ops in `claude --print` headless mode (`Z8()` precondition). **Conditionally auto-enabled**: `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY` — the network-fetch path (which would degrade tool use via the dotted-vs-dashed slug-registry mismatch) stays inert behind `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`, but Phase 3 of the Anthropic-translation shim pre-seeds the discovery cache with the four non-Claude ids and flips the flag on so they appear as `/model` picker rows (cache-READ path applies no id filter and APPENDS, leaving the opus/sonnet/haiku tiers untouched; presence-guarded, a user value always wins). See [`docs/anthropic-translation-shim.md`](docs/anthropic-translation-shim.md) + [`docs/claude-env-injection.md`](docs/claude-env-injection.md).

### Update reliability (Windows-safe), proxy self-update, LLM toolbelt

Three startup behaviors share one Windows-safe exec helper (`src/lib/exec.ts`): `resolveExecutable` (absolute-path resolution against PATH honoring PATHEXT, **excluding cwd** — closes the planted-`npm.cmd` vector) and `buildExecInvocation` (real cmd.exe quoting — caret-escapes `& | < > ( ) ! ^`, refuses `%`; never the naive quote-if-space). On Windows `claude`/`npm` are `.cmd` shims that `execFile` cannot launch, so every child-process call here goes through this helper.

- **Claude Code auto-update** (`src/lib/claude-version-check.ts`): `github-router claude` updates Claude Code on launch via **`claude update`** (install-method-aware — native installer or npm — so it never creates a conflicting second install; not blocked by the `DISABLE_AUTOUPDATER` the proxy sets in the child env via `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`). Builds too old to have `claude update` fall back to `npm install -g @anthropic-ai/claude-code@latest` with a visible warning (never silently strand). Throttled 1h (`last-update-check`); `--auto-update` (default) installs, `--no-auto-update` warns only, `--no-update-check` skips. Cross-process install lock (`src/lib/update-lock.ts`).
- **Proxy self-update** (`src/lib/self-update.ts`): default-ON, throttled (`last-self-update-check`). Probes npm for the **unscoped `github-router`** (the scoped `@animeshkundu/github-router` is GitHub-Packages-only); on a newer version spawns a **detached, post-exit updater** (waits for this PID to exit, then `npm install -g github-router@latest`) — the proxy is a running process, so in-place install would hit Windows file locks (EPERM/EBUSY) and can corrupt the install. Applies on next launch; no re-exec. Disable with `--no-self-update` or `GH_ROUTER_NO_SELF_UPDATE=1`. Wired into `start`/`claude`/`codex` after `setupAndServe`.
- **LLM toolbelt** (`src/lib/toolbelt/`): curated CLI tools (`rg`, `fd`, `jq`, `sd`, `ast-grep`/`sg`, `yq`, `scc`, `difft`/difftastic, `gron`) materialized into `~/.local/share/github-router/bin/` and prepended to the spawned agent's PATH so the model calls them as native. **Gap-fill**: only tools NOT already on the user's PATH are exposed (never shadows a pinned `jq`/Go-vs-Python `yq`). `rg` is materialized from the existing `@vscode/ripgrep` binary (no second download); the rest lazy-download from version-pinned GitHub releases with **hardcoded-in-source SHA256** verified before extraction (`src/lib/toolbelt/manifest.ts`; regenerate via `scripts/gen-toolbelt-manifest.ts`, which takes an optional `--only <csv>` filter to re-pin a subset). `tokei` is NOT bundled (its GitHub releases ship 0 prebuilt binaries since 2024; `scc` is the bundlable code-stats substitute) but stays in the worker `toolbelt` allowlist opportunistically — it runs if the user has it system-installed. Extraction is dependency-free (`extract.ts`) and **regular-files-only** (rejects symlink/hardlink/device archive entries). Materialization runs in the background (never blocks launch); the awareness one-liner is injected into the mirrored CLAUDE.md so the agent knows which tools are on PATH. Anti-shadow: the launcher resolves `claude`/`codex` to an absolute path so the toolbelt PATH can't shadow the CLI itself. Opt out with `GH_ROUTER_DISABLE_TOOLBELT=1`; skip individual tools with `GH_ROUTER_TOOLBELT_SKIP=jq,yq`. The toolbelt PATH also reaches the worker-agent bash env (casing-safe, no global `process.env` mutation), and all worker modes additionally get a `toolbelt` tool (itself read-only) that runs these CLIs with `shell:false` (see "worker tools" below).

### Durable hook launcher and code-search assets

`github-router claude` persists hook commands in the mirrored `settings.json`; a `bunx` entrypoint can instead live under the OS temp root, where cleanup or an in-place `bunx pkg@latest` re-extraction can leave a live session pointing at missing or changing code. `src/hooks.ts` is therefore a separate self-contained build of all nine `internal-*` hook subcommands (`noExternal`, `codeSplitting: false`), published by `src/lib/hook-launcher/` under `~/.local/share/github-router/hooks/hooks-<sha256>.mjs`. The `.mjs` extension removes a runtime-version dependency rather than fixing a live break: Node has detected ESM syntax by default since 22.7, so a relocated `.js` runs correctly on a current runtime even with no `package.json` above it, but on Node 20 (this package declares no `engines` floor) it is read as CommonJS and fails to start.

`resolveSelfInvocation()` is awaited before **any** settings or runtime file persists a self-command. Do not make it fire-and-forget: doing so can store its temporary publication path and leave the session broken even if provisioning later succeeds. The bundle's build-generated `hooks.sha256` must match the bytes before publication. Both a missing/unreadable sidecar and a mismatch are a refusal to publish, because content-addressing a torn in-place extraction would preserve corruption. Published names are immutable digest names, not version names: never garbage-collect them, since concurrent proxies can otherwise delete a launcher that a live session still uses. Same-directory temp-file-plus-rename publishing prevents a partial file being named by a hook.

Every persisted self-command is composed through `buildSelfCommand`. Its relocated form carries `--package-root <root>` as a literal argument, never an environment variable: child environments are filtered, whereas argv survives. The relocated bundle cannot walk to the package root; without the explicit value, browser native-host lookup falls back to the user's workspace and runtime version lookup cannot find the package manifest. Keep `getPackageVersion()` as a runtime read, not a bundled value, because the release build precedes its version bump. Provisioning failure falls back to the original entrypoint and warns only when it is under a volatile temp root.

The same package-tree loss affects code search. `src/lib/code-search.ts` prefers system `rg`, then the durable toolbelt copy, before the package dependency; `src/lib/tree-sitter-assets/` copies the web-tree-sitter runtime and the nine grammar WASMs into APP_DIR. Those copies are best-effort first-run fallbacks, but prevent code search from becoming a hard ripgrep failure or a silent loss of structural ranking and outlines after a reaped package tree.

### Windows keep-awake (default-on, best-effort)

`github-router start`/`claude`/`codex` keep the machine awake while the proxy runs so a long unattended agent session doesn't die to idle-sleep. **Windows-only, on by default** (`src/lib/keep-awake/`): after `setupAndServe` it spawns a **persistent `powershell.exe` helper** (`startKeepAwake()`, fire-and-forget alongside `provisionAndIndexColbert()`) that P/Invokes `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` and blocks on stdin. `SetThreadExecutionState` is **thread-scoped**, so the assertion must be held by a live thread — when the proxy dies (clean exit, SIGINT/SIGTERM, SIGKILL/taskkill, OOM) the stdin pipe closes, the helper hits EOF, clears the assertion, and exits; Windows also releases it on the helper's death. The helper therefore **cannot outlive the proxy**, so no orphan sweep is needed (unlike colbert/worktrees). Released via `stopKeepAwake()` in the `claude` shutdown chain AND the module's own self-registered SIGINT/SIGTERM/exit handlers (the colbert/worker re-raise pattern — load-bearing for `start`, which has no `launchChild`/`onShutdown`). Flags: `GH_ROUTER_DISABLE_KEEP_AWAKE=1` opts out; `GH_ROUTER_KEEP_DISPLAY_ON=1` adds `ES_DISPLAY_REQUIRED` (default keeps system awake but lets the panel sleep).

The script templates the flag as a **decimal `[uint32]` literal, NOT hex** — Windows PowerShell parses `0x80000001` as a negative Int32 that fails the `uint` conversion (verified on a real win32 host). **Mechanism choice** (PowerShell over a bundled `.exe` or koffi FFI): a bundled unsigned `.exe` is refused under enforced WDAC code-integrity, and koffi is a native addon the project avoids; PowerShell adds zero artifacts and works wherever `Add-Type` is permitted. **Best-effort degradation** — when the assertion can't be set (Constrained Language Mode blocks `Add-Type`, no `powershell.exe`), the helper prints no `OK` readiness line and we `consola.debug` a no-op; we **never install, enable, or bypass** language-mode/WDAC policy, and never block launch. Full mechanism-decision record (CLM/WDAC/EDR trade-offs, crash-safety proof) in [`docs/windows-keep-awake.md`](docs/windows-keep-awake.md).

### `apiKeyHelper` and external credential scripts

The user's `settings.json` is mirror-copied into `CLAUDE_CONFIG_DIR` at startup so any `apiKeyHelper` / `awsCredentialExport` / `awsAuthRefresh` / `gcpAuthRefresh` defined there still fires inside the proxy session. The proxy supplies auth via the synthetic `claudeAiOauth` blob in `<CLAUDE_CONFIG_DIR>/.credentials.json`; if a user's helper mints an additional `x-api-key` header it's sent alongside our Bearer (Copilot ignores `x-api-key`). See [`docs/auth-isolation.md`](docs/auth-isolation.md).

**MCPs**: user-scope and local-scope MCPs are stored in `~/.claude.json`, which is MIRRORED (snapshot-copied at proxy startup). To register MCPs that persist across `github-router claude` launches, add them via plain `claude mcp add` (or edit `~/.claude.json` directly) *outside* a proxy session — the next launch's snapshot will pick them up. MCPs added inside a proxy session are session-scoped and lost when that session ends; this is by design (the mirror is one-way snapshot, not write-back, to keep the proxy's session state isolated from the user's real config). **Subagent MCP visibility**: the scoped servers (`peers`, `search`, `workers`, `orchestrate`, `decide`, plus `browser` under `--browse`, and the `codex-cli` stdio entry when `--codex-cli` is in effect) are merged into the mirrored `.claude.json`'s `mcpServers` so Agent-tool subagents, forks, and agent-teams subprocesses inherit them. Project-scope `<workspace>/.mcp.json` is untouched — spawned `claude` inherits the parent's cwd and reads it directly. Subagent `.md` frontmatter intentionally omits `tools:` (omission inherits the parent's full toolset; adding `tools:` would *restrict*). On collision with a user-side entry of one of our bare keys, `resolveGroupKeysFromMirror` walks `gh-router-<group>`, `gh-router-<group>-2`, … to the first free name (threaded into both the entry and the persona `.md` routing string) rather than dropping the group — it never skips and never reuses a user-owned name. If the whole mirror injection fails (unwritable), the proxy falls back to ephemeral `--mcp-config` for the parent session only (subagents degraded — visible at startup in the `subagent-INVISIBLE` banner).

### Native subagents (implementer / implementer-fast / reviewer / brainstorm / scout / scribe / general-purpose-fast)

`github-router claude` injects four native subagents unconditionally, plus three more when their model chains resolve: `implementer` (you know what to build), `reviewer` (something exists and you want it assessed, including reproducing and root-causing a failure), `brainstorm` (you do not yet know which approach to take), `scribe` (docs and ADRs that trail the code), `scout` (find or understand something in the repo, cheaply), `implementer-fast` (the well-specified, mechanical coding change), and `general-purpose-fast` (the catch-all for work no specialist fits). When a preferred model chain misses, the four unconditional agents omit `model:` and inherit the lead; the three conditional ones are dropped rather than inheriting an expensive lead model. `reviewer` is the rename of the former `qa-engineer` and absorbed the former `debugger`'s job: giving feedback requires whatever analysis that takes. Unlike the peer critics (thin subagents that route to their verdict model via MCP while themselves running on the inherited Claude model), these RUN on the selected model: their frontmatter sets `model:` when that id is in the catalog (a full model id, passed through uninspected behind our custom base URL — subagent traffic hits the same `/v1/messages` shim as the main loop, tagged `x-claude-code-agent-id`). **Per-agent model resolution** lives in `src/lib/mcp-capabilities.ts`, all resolvers sharing one `firstPresentInCatalog(chain, {requireToolCalls, minContextTokens})` walk: `nativeSubagentModel()` (`implementer` only) → `gpt-5.6-sol` → `gpt-5.5` (public coding benchmarks put sol ahead of both `gpt-5.6-terra` and `gpt-5.3-codex`, so the cheaper tiers are a cost trade this project's rules say not to take); `reviewerModel()` → `gemini-3.1-pro-preview` → the frontier chain, **deliberately NOT the implementer's model** — sharing one resolver meant a review of implementer-produced work was one model checking its own output, which two independent blind audits flagged and which `worker-review` already avoids for the same reason; `brainstormModel()` → `gemini-3.1-pro-preview` → the frontier chain (a third lab, since the Anthropic lead is the producer and the OpenAI frontier already backs implementer/reviewer, so a same-lab brainstormer would mostly restate what the lead thought of); `scribeModel()` → `gpt-5.6-terra` → the frontier chain; `scoutModel()` → `gpt-5.6-luna` → `gemini-3.6-flash`; `generalPurposeFastModel()` → `gpt-5.6-luna` (single entry). **The chains are built inside the resolvers, never as module-level consts** — `./worker-agent` is in an import cycle with `mcp-capabilities`, so a top-level `const CHAIN = [REVIEW_DEFAULT_MODEL]` throws `Cannot access ... before initialization` at load. **`scout`, `implementer-fast`, and `general-purpose-fast` are DROPPED rather than downgraded** when their chain misses: being cheaper than the lead's model is their entire purpose, so inheriting Opus would burn exactly the cost they exist to avoid; every other native omits its `model:` line and inherits the lead. **`scout` and `brainstorm` carry a read-only `tools:` allowlist** (`READ_ONLY_TOOL_ALLOWLIST`, modelled on the CLI's own `Explore`/`Plan` which keep Bash but drop Edit/Write/NotebookEdit/Agent); `tools:` is positive-only with no "all except" form, so the cost is that those two do NOT inherit user-scope MCPs or tools added by later Claude Code releases — accepted because a prompt asking an agent not to write is not enforcement while Edit/Write are inherited. The workers and orchestrate MCP groups are excluded on the same reasoning that makes `Explore` drop `Agent`: they spawn further agents. Every other native carries NO `tools:` field and inherits the full toolset. The model is OVERRIDABLE at spawn: frontmatter `model:` is resolution rank #3, so a per-invocation `model` param (rank #2) still wins — this is WHY the injection uses per-subagent frontmatter and NOT the global `CLAUDE_CODE_SUBAGENT_MODEL` env var (rank #1, a HARD override that would suppress the per-invocation choice and violate "overridable at init"). Wired via `buildPeerAgentDefinitions` / `buildAgentMd` in `src/lib/codex-mcp-config.ts`, threaded from `src/claude.ts` and `src/lib/serve/enhancements.ts`. `ALL_NATIVE_AGENT_NAMES` (same file) is what the sweep-allowlist drift test iterates, and every name must ALSO be added to `PEER_AGENT_MD_FILENAME` in `src/lib/paths.ts` or a crashed session's `.md` survives forever as a ghost subagent. Retired names stay in that regex permanently so crashed prior-session files remain sweepable. When a request carries no `thinking` block the shim defaults to `high` (1:1 level mapping); opt into the old frontier `xhigh` default with `GH_ROUTER_FRONTIER_XHIGH_DEFAULT=1`. Explicit client thinking always wins — there is deliberately no per-agent effort knob, so a subagent's reasoning effort follows the Claude Code effort picker. **Review decorrelation**: because bounded implementation trends gpt-5.6-sol/OpenAI (these subagents + the `implement`/`test` workers), `REVIEW_DEFAULT_MODEL` is `gemini-3.1-pro-preview` (Google, cross-lab) so the worker reviewer's lab is decorrelated from the implementer's and the Opus orchestrator's.

**The `implementer` / `implementer-fast` split, and the `general-purpose-fast` catch-all.** `implementerFastModel()` → `gpt-5.6-terra` → `gemini-3.1-pro-preview`; `generalPurposeFastModel()` → `gpt-5.6-luna` (single entry). Both carry the full toolset, which is what separates them from `scout` — a read-only agent could not finish the work it is handed. `implementer-fast` was renamed from `generic` (a catch-all framed as "work no specialist fits") because that framing was the weakest possible delegation trigger: it described the ABSENCE of a fit rather than a job, so the lead almost never picked it over working inline. It now names a job — the well-specified, mechanical coding change — and `implementer` carries the reciprocal clause for changes needing judgment or with ambiguous scope. `general-purpose-fast` keeps the true catch-all boundary and carries the `Use proactively` idiom that Claude Code's auto-delegation rubric keys on. Four constraints are load-bearing:

- **`implementer-fast` and `general-purpose-fast` pass `minContextTokens: ONE_M_TOKENS`**, so the 1M window their descriptions promise is enforced by the resolver rather than asserted in a comment. Without it, a catalog id whose advertised window shrinks is still selected, `withOneMSuffix` silently omits the `[1m]` bracket, and the agent is budgeted at Claude Code's 200K default with no signal. **`scoutModel()` takes the floor too**: its chain is `gpt-5.6-luna` → `gemini-3.6-flash`, and the former `gpt-5.4-mini` (400K) last resort was dropped. That tail previously existed because mini's `restricted_to` is the widest of the three (it includes `individual_trial` and `edu`); the accepted consequence is that `scout` is now DROPPED on a catalog carrying neither 1M model rather than degrading to a 400K scout.
- **`gpt-5.6-sol` is absent from `implementer-fast`'s chain** — the OpenAI frontier coder is already `implementer`'s job, and the fast tier quietly billing at frontier rates is the opposite of the point.
- **`general-purpose-fast` is single-entry.** `gpt-5.6-luna` is the cheapest model in the live catalog, carries 1.05M context and the full `none…max` effort ladder, and measured fastest among the catch-all candidates. No `-mini`/`-lite`/`-haiku` model in the catalog serves 1M (the conventional cheap tier tops out at `gpt-5.4-mini` = 400K), which is why the catch-all is a `gpt-5.6-*` slug.
- **A description may claim only what is true of EVERY member of its chain**, because the fallback is invisible to whoever reads the prose. `implementer-fast` may not mention a `max` effort tier (terra has one, gemini-pro does not). `general-purpose-fast` has one chain member, so its description may state Luna's measured speed, catalog cost, context, and effort properties exactly. **`implementer-fast`'s NAME remains the one place that rule is knowingly bent**: `gemini-3.1-pro-preview` is a `pro` model, so on the fallback path "fast" is not true of the resolved model. The DESCRIPTION contains the bend by claiming speed/cost only when `gpt-5.6-terra` won and describing the Gemini path neutrally.

**The former open question is answered by measurement.** The test preregistered here was specific: time an identical trivial TOOL-CALLING task against both models, because tool-call latency, not prose generation, is what an agent model spends its turns on. Run on that workload on 2026-08-12 (`bun scripts/bench-model-speed.ts`, median of n=3), `gpt-5.6-luna` reached a tool call in 928 ms versus 2553 ms for `gemini-3.6-flash` and 2163 ms for `gemini-3.5-flash`, all three at identical 3/3 tool-call reliability. Generation throughput ordered the same way (~120 vs ~45 vs ~40 output tokens/s). Live catalog prices per 1M tokens were Luna 20/120, Gemini 3.6 Flash 150/750, Gemini 3.5 Flash 150/900, with contexts 1.05M / 1.00M / 1.00M. So the entire `generic-fast` chain was dominated by Luna on tool-call latency, generation speed, input price, output price, and context. The preregistered consequence was applied: delete `generic-fast`, rename `generic-cheap` to the earned `general-purpose-fast`, and keep one catch-all rather than two overlapping entries. **The harness is committed precisely so these numbers can be re-derived and challenged** — an earlier ad-hoc n=1 pass put `gpt-5.6-sol` at 22 tokens/s and `gemini-3.1-pro-preview` at 9, both wrong by 3x because time-to-first-token dominates a short response. Re-measure before trusting any figure here; the constants are rounded coarsely because run-to-run variance is large.

**The bigger open question, and the instrument now built for it**: until recently NOTHING in this repo had ever measured whether an unprompted lead actually delegates to any of these agents. `codex-mcp-config.ts` carried a ~60% ESTIMATE for the `Use proactively` polling loop and specified an acceptance test — under 7/10 sessions delegating, wire a deterministic `ExitPlanMode` PreToolUse hook — and that test was never run, so the fallback was never wired. Every roster decision above therefore rested on judgement, not evidence. `scripts/eval-delegation.ts` (opt-in via `GH_ROUTER_RUN_DELEGATION_EVAL=1`, preregistered in `docs/review/subagents/DELEGATION-EVAL.md`) is the instrument: three SEPARATE estimands (spontaneous delegation, routing into an ACCEPTABLE SET rather than one hand-picked answer, and restraint on negative controls where working directly is correct), a stratified battery instead of one canonical prompt per agent, and randomized interleaved A/B instead of a sequential before/after that model-alias and CLI drift would confound. Two honesty constraints are baked in: a falling raw `implementer` rate may be SUCCESSFUL migration to `implementer-fast` rather than degradation, so non-degradation is judged only on the complex-implementation stratum; and the eval is expected to be UNDERPOWERED to prove non-degradation, so a null result must be reported as "no drop observed, underpowered to exclude one" and never upgraded into a safety claim. Do not tune a name or a trigger on a hunch when this instrument can be run instead.

**Never name a droppable agent in a static prompt.** `OPERATING_DEFAULTS_DIRECTIVE` (`src/lib/claude-md-injection.ts`) is built per launch by `buildOperatingDefaultsDirective(opts)` and omits the clause for each agent that launch did not emit; `buildPeerAwarenessSnippet` takes the same booleans. Resolve availability ONCE per launch (`nativeAvailability` in `src/claude.ts` / `src/lib/serve/enhancements.ts`) and reuse it across the `.md` generation, the awareness snippet, and the directive, so the three surfaces cannot disagree. The directive previously named `scout` unconditionally despite `scout` being droppable, which on a thin catalog told the lead to delegate to an agent with no `.md` file and no entry in the Task `subagent_type` enum. Pinned by a regression test in `tests/isolated/claude-md-injection.test.ts` that builds with the flags false and asserts the omission — the all-available const contains every name, so a roster assertion alone would pass either way.

### Peer-model MCP integration (auto-invocation, effort, decomposition)

The `claude` subcommand auto-injects peer-model review tools as Claude Code subagents (`codex-critic` gpt-5.6-sol, `codex-reviewer` gpt-5.3-codex, `gemini-critic` gemini-3.1-pro-preview, and `gemini-reviewer` gemini-3.1-pro-preview at highest reasoning — a second-lab line-level reviewer, registered alongside `gemini-critic` whenever a `gemini-3.x-pro` model is in the catalog) plus a `peer-review-coordinator` meta-subagent. Each persona accepts an `effort?: "low"|"medium"|"high"|"xhigh"` argument; per-persona `allowedEfforts` table, the SSE-streamed `/mcp` xhigh-default rationale, the latency-by-effort matrix, and the predictedTooLong pre-flight cap live in [`docs/peer-mcp-design.md`](docs/peer-mcp-design.md). Concurrency cap `MAX_INFLIGHT_TOOLS_CALL` (default 128, override `GH_ROUTER_MAX_INFLIGHT_TOOLS_CALL`; single shared counter in `src/lib/mcp-inflight.ts`; both MCP-boundary persona calls in `src/routes/mcp/handler.ts` AND nested `peer_review`/`advisor` calls inside the worker tools acquire from the same slot — so a worker can't fan out unboundedly and starve operator traffic). **Decomposition is the load-bearing fix for Claude Code v2.1.113+'s MCP per-tool-call timeout regression ([#50289](https://github.com/anthropics/claude-code/issues/50289)); the `MCP_TIMEOUT`/`MCP_TOOL_TIMEOUT` (default `22500000` ms = 6h15m, override `GH_ROUTER_MCP_TOOL_TIMEOUT_MS`, resolved by `resolveMcpToolTimeoutMs()` in `src/lib/worker-agent/budget.ts`) env injection both backstops it and gives autonomous workers room to run (the 6h worker wall-clock sits exactly 15 min under it).** Two non-negotiables when touching `src/routes/mcp/handler.ts`: (1) the `predictedTooLong` cap MUST fire before the `acquireInFlightSlot()` call (don't reorder — leaks concurrency slots on every reject); (2) `sweepStalePeerAgentMdFiles`'s regex requires the digit-PID prefix — relaxing it would delete user-authored files like `peer-reviewer.md`.

**Six intent-named MCP servers (server split).** The MCP surface is split into SIX scoped servers, each a distinct `mcpServers` entry pointing at a path-scoped `/mcp/<group>` endpoint, so the server name signals the tool category to the model instead of burying everything under one opaque `gh-router-peers`: `peers` (the critics + `gemini_reviewer` when a `gemini-3.x-pro` model is served + `codex_implementer` in `--codex-cli`), `search` (`code`, `web`), `workers` (`explore`, `review`, `implement`, `plan`, `test`), `orchestrate` (the workflow tools `decompose`, `verify_workflow`, `run_workflow`, `attest_step` — a distinct category from `workers`: these compose/verify/run/audit a workflow, whereas the workers are what a workflow delegates to; `verify_workflow`/`attest_step` are pure + always-on, `decompose`/`run_workflow` share the worker backend gate), `browser` (the `browser_*` tools, renamed — only with `--browse`), and `decide` (`stand_in`). The model sees `mcp__search__code`, `mcp__browser__navigate`, `mcp__peers__codex_critic`, etc. The single source of truth is `GROUP_META` + the `group` field on each tool in `src/lib/peer-mcp-personas.ts`; `assertMcpToolSurfaceConsistent()` (called at server boot) pins per-group + cross-union name uniqueness. **Config keys are bare** (`peers`/`search`/…); on collision with a user-side `mcpServers` entry, `resolveGroupKeysFromMirror` (in `src/lib/codex-mcp-config.ts`) walks the numbered fallback sequence `gh-router-<group>`, `gh-router-<group>-2`, … until it finds a free name, and threads the RESOLVED key into BOTH the `mcpServers` entries AND the persona `.md` routing strings — so a user's own `browser`/`search` MCP never silently hijacks or drops one of ours. It **never skips and never returns a name the user owns**: every enabled group is guaranteed a proxy-owned key, so a capability is never dropped and the model is never routed at the user's same-named server. The route (`src/routes/mcp/route.ts`) accepts `POST /mcp/:group` (scoped) and `POST /mcp` (the full union, retained for BYO `start`/`codex` clients); the handler filters `tools/list`/`tools/call` by URL scope (wrong-scope call → -32601). **Tool renames are MCP-facing only**: `code_search`→`code`, `web_search`→`web`, `worker_explore`→`explore`, `worker_implement`→`implement`, `browser_*`→strip the prefix; persona names and `stand_in` are unchanged. For browser tools the rename is applied at the `NON_PERSONA_MCP_TOOLS` spread, leaving the wire `tool` string the installed MV3 extension dispatches on (`browser_navigate`, …) physically unchanged in `src/lib/browser-mcp/index.ts` — so **no extension reload is needed**.

The same `/mcp` surface also exposes two non-persona utility tools (group `search`) that all clients see: `web` (Copilot-backed web search, was `web_search`) and `code` (was `code_search`). **`code` is semantic-first:** its default `mode: "semantic"` ranks by MEANING via ColBERT (the former standalone `semantic_search` tool, folded in here) and transparently falls back to lexical BM25F when the per-workspace index isn't ready, labelling a 3-valued `source` (`semantic` | `lexical` | `lexical-fallback`) so a degrade is never silent; semantic-ready rows additionally carry a ColBERT `score`. The `mode` enum is `semantic|lexical|exact|regex|ast`; the shared router is `src/lib/unified-code-search.ts` (`runUnifiedCodeSearch`). The BM25F / ranking / `complete` / `scan` / `ast_pattern` behavior described below is the LEXICAL path (`lexical` = the former `ranked`, `exact` = the former `literal`), reached by the forced modes and by the semantic fallback. `code` runs ripgrep with BM25F ranking (Robertson, Zaragoza, Taylor 2004) over four code-aware fields (matched line, surrounding context, file path tokens, symbol-definition heuristic), then refines the symbol-context field with tree-sitter AST analysis on the top hits (`structural: "full"` → top 50, `structural: "topN"` → top 10) so identifier definitions outrank incidental string matches. Tree-sitter passes are wrapped in a 200ms wall-clock budget; on exhaustion remaining hits drop back to the regex heuristic for that one file. The MCP response includes one optional `notice: string` field, present iff an actionable degradation fired — either the structural budget exhausted, or the 256KB response-size cap truncated the result set; the message text tells the model what to retry (`structural: "topN"`, narrow query, lower limit). The default `limit` is 200 (raised from 20 for exhaustive enumeration), and `summary` is ON BY DEFAULT — both semantic and lexical responses carry an `outlines` field: a compact tree-sitter map of navigable declarations (top-level symbols and class members, omitting function-local noise) for the distinct files in the result set (first 10, in result order, via `outlineFile` in `src/lib/tree-sitter-grammars.ts`). It augments, never replaces, each hit's `snippet` (set `summary: false` to omit it; outlines are budget-fitted after results so they never breach the 256KB envelope). In the lexical path a per-file `--max-count` (`RANKED_MAX_PER_FILE`) plus a shoulder cut (drop hits below 50% of the top score) keep one match-dense file from exhausting the 200-hit global limit and keep the model from being flooded — but BOTH are default-only precision filters: passing `complete: true` disables them and returns the full ripgrep match set (reordered, capped only by `limit`) — the recall floor in [`docs/code-search-floor.md`](docs/code-search-floor.md) applies to that lexical path: in `complete` mode it drops nothing by its own heuristics (only the explicit `limit`), is a superset of naive `rg <identifier>` for single ASCII identifiers, and is `=` the ripgrep it runs (the doc is precise that it does NOT subsume ast-grep's multi-line patterns or a full-workspace tree-sitter scan). When the default prune hides matches the response `notice` says so and points at `complete: true`, so a miss is never silent; and a hit carries `role: "definition"` only when the structural pass AST-confirms it (absence is never a "usage" claim). Single-identifier queries in the lexical modes are auto-expanded across camelCase / snake_case / kebab-case / SCREAMING_SNAKE skeletons before being passed to ripgrep (`getUserName` also finds `get_user_name`). Workspace is any absolute path the proxy process can read — no allow-set, no secret-shape file denylist. The threat model is symmetric (Claude Code already has Read / Bash / Edit that reach the same paths), so gating one tool was inconsistency, not defense. Ripgrep itself comes from `@vscode/ripgrep` (per-platform binary via optionalDependencies) with system-PATH `rg` preferred when available. The MCP handler trims the rich internal response to `{file, line, snippet}` per hit (plus `role`/`endLine`/`name`/`score` where present) and a tiny envelope carrying the top-level `source` before stringifying — internal diagnostics (BM25F scores, field contributions, scanned-files, elapsed-ms, ranking-metadata block) are intentionally NOT forwarded; see the "Design principle: ruthlessly minimal MCP tool surface" section in [`docs/peer-mcp-design.md`](docs/peer-mcp-design.md) for the per-field rationale. Implementation: `src/lib/unified-code-search.ts` (router) + `src/lib/code-search.ts` (lexical backend) + `src/lib/colbert/` (semantic).

`/mcp` also exposes three **worker tools** (group `workers`: `explore` read-only, `review` read + `bash`, `implement` read+write — `explore`/`implement` were `worker_explore`/`worker_implement`) that delegate scoped work to an **autonomous Pi-runtime worker subagent** (the vendored Pi runtime lives at `src/vendor/pi/`; the sync protocol is in [`docs/pi-vendor-sync.md`](docs/pi-vendor-sync.md)). **Per-mode model defaults** (caller `model` arg always wins; all resolved against the live catalog with thinking clamped to the model's `reasoning_effort` allowlist): read-only `explore` → `EXPLORE_DEFAULT_MODEL` = `gpt-5.6-luna` at `high` (via `EXPLORE_DEFAULT_THINKING`; Luna's full effort ladder makes `high` a real choice rather than a clamp; measured cheaper and faster than the former Gemini Flash default, with a larger context window; NOT a gate input — errors at call time if absent, like `implement`'s gpt-5.6-sol); read-only `review` → `REVIEW_DEFAULT_MODEL` = `gemini-3.1-pro-preview` at `xhigh` (clamped to `high` — gemini has no xhigh; a cross-lab reviewer deliberately decorrelated from the gpt-5.6-sol implementer/`implement` worker + the Opus orchestrator, for blind-spot diversity); read-only `plan` → `PLAN_DEFAULT_MODEL` = `claude-opus-5` (DOTTED catalog id — the worker resolver exact-matches `catalog.id`; `claude-opus-5` is a single-segment slug so dotted == dashed) at `high` (planning is the highest-leverage step, so it gets the strongest model, not a cheaper default; errors helpfully at call time if opus-5 is absent, like `implement`'s `gpt-5.6-sol`); read+write `implement`/`test` → `IMPLEMENT_DEFAULT_MODEL` = `gpt-5.6-sol` at `high` (the default favours time-to-outcome; precedence is per-call `thinking` > `worker_defaults` session override > built-in, so a caller restores `xhigh` whenever the work warrants it); `browse` → `BROWSE_DEFAULT_MODEL` = `gpt-5.6-luna`. All six mode constants (including the independent `TEST_DEFAULT_MODEL`) and the general `DEFAULT_MODEL_CHAIN` live in `src/lib/worker-agent/engine.ts` (single source of truth, re-imported by the gate — no parallel constant to drift). **Session defaults:** the `worker_defaults` MCP tool sets process-global, in-memory model/thinking overrides per mode. Resolution precedence is per-call override > session override > built-in. **Catalog discovery:** a zero-arg (inspect) call additionally returns a `catalog` array — the live-catalog models a worker can actually be pointed at (`tool_calls`, a worker-requestable `reasoning_effort`, and >= 200k context), each row `{id, vendor, ctx, maxOut?, efforts, in?, out?, tps?}` from `buildCatalogView()` in `src/lib/worker-agent/model-resolve.ts` (~19 rows / ~2.4 KB on an enterprise catalog). `in` and `out` derive from the live catalog's batch-sized `billing.token_prices`, normalized to per-1M-token relative units and omitted when absent or malformed. `tps` is an approximate, indicative output-tokens/sec hint from a small dated measurement table, not a per-call benchmark. It exists because the hardcoded chains cannot DISCOVER anything — models ship live that appear nowhere in `src/` (`gpt-5.6-luna`, `grok-4.5`), so nobody evaluates them. Three deliberate constraints: it is **derived only except for the explicitly labelled, recoverable speed hint**; it exposes no reasoning, quality, intelligence, or benchmark score because that editorial prose rots silently as vendors ship, and a WRONG characterization misroutes invisibly while a MISSING one costs one recoverable pick. `efforts` is **clamped to `WORKER_THINKING_LEVELS`** so the `max` tier nine live models advertise is never offered when no worker can request it; and it rides **only on inspect**, never on a set/clear, so the bytes are paid on the call that asked for them. `vendor` is included so a caller can reason about LAB DIVERSITY — the per-mode and per-agent defaults stay hardcoded precisely because they encode cross-lab DECORRELATION (`reviewerModel()` must differ from the implementer's lab), which no capability table can express. Verified workflow producer runs explicitly ignore session defaults so cross-lab isolation cannot be changed behind the IR's declared labs; gate discovery remains advisory and intentionally honors the explore override. **Model-override tier ladder** (surfaced in the `model` param description of `explore`/`implement`/`review` via `WORKER_TIER_GUIDANCE` in `src/lib/peer-mcp-personas.ts`): the caller picks by task weight — `gpt-5.6-sol` (heavy/deep), `gpt-5.6-terra` (moderate), `gpt-5.6-luna` (light/cheap), all 1M-context, recommended at `high`. It is prose guidance layered on the free-string `model` param (no `enum` — the runtime still validates against the live catalog), so the per-mode defaults above stay the safe default while the caller can right-size per call. **`review` is a third worker mode** (`WorkerAgentOpts.mode`): explore's read-and-search surface PLUS `bash` unconditionally (so it VERIFIES — reproduces a failure, runs the build or suite — rather than only reading), gaining `edit`/`write` only when the caller opts into `worktree: true`. `systemPromptFor("review")` adds a one-line reviewer ROLE frame (verify correctness against the actual code, report findings with severity + `file:line`) — role framing, not prescriptive step-advice, so it keeps faith with the no-scaffolding prompt principle. Because it holds `bash` in both modes it is NOT a read-only worker and must never be described as one. Unlike the stateless `peers` critics, the `review` worker can navigate the repo to check surrounding context itself. **Worker toolset:** explore/review expose 9 read-only tools — `read`/`glob`/`grep`/`code_search` (semantic-first via the shared `runUnifiedCodeSearch`, so workers get ColBERT + transparent lexical fallback too)/`web_search`/`fetch_url` plus a read-only `toolbelt` tool (runs `rg`/`fd`/`sg`/`jq`/`yq`/`gron`/`scc`/`tokei`/`difft`/read-only `git` with `shell:false` — args are literal, write/exec flags and mutating git subcommands rejected), `advisor` (consult a stronger cross-lab model on a focused concern; it sees the recent transcript via the engine's `getMessages` closure over `agent.state.messages`) and `update_plan` (a stateful planning checklist re-surfaced each turn by the engine's `transformContext` hook so it survives compaction — `appendPlanReminder` in `engine.ts`); implement adds `edit`/`write`/`bash`/`codex_review` (13 total). Workers are TERMINAL — no sub-worker spawning — and `peer_review` is deliberately NOT wired in (peer critics aren't part of the worker surface; `advisor` is the consultation path). Implement mode is no longer forced agent-wide sequential: pure read/search batches run in parallel, while `edit`/`write`/`bash`/`codex_review`/`update_plan` each declare `executionMode:"sequential"` so Pi serializes any batch containing one of them (a write/stateful tool never runs concurrently). Dual gate: `workerToolsEnabled()` drops all worker tools from `tools/list` AND `tools/call` when `GH_ROUTER_DISABLE_WORKER_TOOLS=1` OR no model in the ordered gate/fallback chain `gpt-5.6-luna` → `gpt-5.4-mini` is present with `tool_calls`. The catalog itself is the tier signal: Luna wins where entitled, while mini preserves the worker surface on `individual_trial` and `edu`; never infer the user's tier from a model's `billing.restricted_to`. Explore's and implement's per-mode defaults are NOT gate inputs — if a default is absent, that mode errors helpfully at call time rather than the whole worker surface vanishing. The worker tools take a `workspace` (absolute path) resolved as **explicit argument > the per-connection `X-GH-Workspace` session header > refuse**; there is deliberately NO launch-cwd default, because the proxy is started once from wherever the operator was while the calling agent may since have moved into a git worktree, so `process.cwd()` silently ran workers against a tree without the files they were asked about. A call carrying neither returns an actionable `isError` (operator escape hatch for raw MCP clients: `GH_ROUTER_ALLOW_PROXY_CWD_WORKSPACE=1`), and whenever the workspace was not chosen by the CALLER the result is prefixed `[workspace: <path> (<source>)]` so a wrong-tree run is visible — `applySessionWorkspace` returns that provenance because merging the header into `args.workspace` otherwise makes the two indistinguishable. Absolute-only enforcement at the MCP boundary in `runWorkerToolCall` so a typo doesn't silently resolve against `process.cwd()`. The `worker-*` dispatchers (the only callers the PreToolUse guard admits) are instructed to ALWAYS pass their own cwd, so the sanctioned path never depends on a stale header; persona `imagePaths` confinement is rooted at the same session workspace. Budget caps (`Budget` in `src/lib/worker-agent/budget.ts`): max turns 500 (`GH_ROUTER_WORKER_MAX_TURNS`), per-model-call timeout 15 min (`GH_ROUTER_WORKER_MODEL_CALL_TIMEOUT_MS`; covers fetch plus SSE consumption and retries exactly once only before model output), max wall-clock 6h (`GH_ROUTER_WORKER_MAX_WALLCLOCK_MS`, plus a per-call `maxWallClockMs` arg — both clamped to `workerWallClockCeilingMs()` = the injected `MCP_TOOL_TIMEOUT` MINUS a 15-min teardown headroom (`MCP_TIMEOUT_HEADROOM_MS`), default `MCP_TOOL_TIMEOUT` 6h15m via `resolveMcpToolTimeoutMs()`/`GH_ROUTER_MCP_TOOL_TIMEOUT_MS`, so a non-converging worker aborts GRACEFULLY and returns its partial work + `[halted: wallclock]` a full headroom BEFORE the harness hard-kills the call, instead of returning nothing), max cumulative tool-output bytes 16 MiB (`GH_ROUTER_WORKER_MAX_TOOL_BYTES`), max tool calls 250 (`GH_ROUTER_WORKER_MAX_TOOL_CALLS`), max CONSECUTIVE identical tool calls 3 (`GH_ROUTER_WORKER_MAX_REPEATED_CALLS` — the duplicate-read / anti-loop guard; blocks the repeated call without halting the run), advisor transcript chars 720 000 (`GH_ROUTER_WORKER_ADVISOR_MAX_CHARS`, matches `ADVISOR_MAX_CONVERSATION_CHARS` in `src/services/advisor/advisor.ts`). **No-output nudges**: when a run stops CLEANLY but emits no usable text (the model occasionally ends a turn right after a tool call without summarizing), the engine enqueues up to `MAX_EMPTY_OUTPUT_NUDGES` (3, override `GH_ROUTER_WORKER_MAX_NUDGES`; `0` disables) follow-up user turns IN THE SAME RUN before surfacing the `[worker exited with no output …]` sentinel. Nudging beats the earlier whole-run retry because it preserves the accumulated transcript instead of discarding it. `shouldNudgeForEmptyOutput` (`engine.ts`) fires ONLY for `stopReason === "stop"` with no `toolCall` parts and empty text — so `stopReason: "length"` (a truncated turn) and `"toolUse"` are NOT nudge-eligible and reach the sentinel immediately with `after 0 nudges`. Budget caps (`WorkerAbort` → halt message), stream errors (`stopReason="error"` → overflow/upstream diagnostic), and real failures carry distinct messages and are not nudged. **Known gap**: `finalText` is overwritten on every assistant `message_end`, so a later empty turn CLOBBERS an earlier turn's text — on a read-only worker (explore/review/plan) whose transcript is never persisted, a long investigation that ends empty is unrecoverable. `implement`/`test` are unaffected: the worktree diff is composed into the result, so a real code change suppresses the sentinel and the diff is preserved. **Context management** (all worker modes, model-agnostic): a per-run `ContextBudget` (`src/lib/worker-agent/context-budget.ts`) sized from the resolved model's catalog window drives three defenses that never drift — structural model-free compaction via Pi's `transformContext` hook (`compaction.ts`: byte-floor trigger, `structuredClone` before mutating, stub old tool-results/bash-output/tool-call-args oldest-first + current-turn truncation, never orphaning a `toolCall`↔`toolResult` pair), a dynamic per-result `afterToolCall` cap (`tool-output-cap.ts`, ~30% of the window so most pages fit one read), and a request-boundary backstop in `stream-fn.ts` (covers BOTH chat and `/responses`) that stops a predicted overflow with a visible diagnostic instead of an opaque upstream 4xx. If catalog window metadata is absent/invalid, a 128k fallback keeps compaction and per-result capping active, but the request backstop only warns and proceeds because upstream remains authoritative for the unknown real window. **No token/cost accounting** — model-agnostic proxies hit the runaway-loop concern without per-model tokenizer duplication. `implement`/`test` ALWAYS run in an isolated git worktree (the `worktree` arg is RETAINED for schema compatibility but ignored — always `true`, `worktree:false` is overridden with a note; for in-place edits use the native `implementer` subagent), and `review` takes one only when the caller passes `worktree: true` (opt-in: `createWorktree` replays tracked-dirty + untracked-not-ignored files but NOT ignored build inputs, so an isolated reviewer often cannot run the very suite that makes a review a verification). They return the diff via a saved patch file under `PATHS.WORKER_DIFFS_DIR` (`finalize()` in `worktree.ts`: a `--stat` summary + a bounded UTF-8-safe preview + the `.patch` path; a small diff `<= PREVIEW_CAP` (8 KiB) inlines in full). No-git is a HARD ERROR pointing at `implementer`. Worktree cleanup: per-call auto-clean `finally` + session-end SIGINT/SIGTERM sweep + boot-time PID+UUID-gated sweep — the digit-PID prefix is load-bearing, do NOT relax. **Relay-safe results (all modes):** every worker result is passed through `relaySafeText` (`src/lib/worker-agent/relay-cap.ts`) as the FINAL transform at the MCP boundary (`runWorkerToolCall`/`runBrowseToolCall`, AFTER the clampNote prefix and browse-session suffix), so a result over `GH_ROUTER_WORKER_MAX_RESULT_BYTES` (default 16 KiB, clamped `[8,20]` KiB — safely under Claude Code's 25k-token MCP result cap even at ~1 byte/token dense output) spills IN FULL to a `WORKER_DIFFS_DIR/*.txt` file and returns a bounded preview + the path instead of being truncated at the relay. `sweepAgedWorkerDiffs()` (7-day, strict `<pid>-<8hex>.(patch|txt)` name match) reaps both `.patch` and `.txt` on each spill write. **The spill is stated in every worker tool's DESCRIPTION** (`WORKER_OVERSIZED_RESULT_NOTE` in `src/lib/peer-mcp-personas.ts`, appended to all six): the mechanism always worked, but nothing told the model, so a truncated result arrived with a path it had to infer was real and readable from the trailer alone. The two genuinely read-only modes (`explore`, `plan`) additionally carry `WORKER_READ_ONLY_NOTE` — "read-only toolset" describes what the WORKER may do, not what the caller GETS BACK, and a model can read the former and still expect a report file to be left behind. `implement`/`test`/`browse`/`review` deliberately do NOT carry it (pinned by a negative test, since a blanket append would tell the model `implement` cannot change files, and `review` holds `bash`). Worker `bash` runs through a **strict env allowlist** (NOT denylist) with `cmd.exe /d /s /c` on Windows and POSIX `/bin/bash -c` (no `.profile`/`.bashrc`) elsewhere, plus `taskkill /T /F` process-tree kill on Windows; **all `GH_ROUTER_*`, `GITHUB_TOKEN`, `ANTHROPIC_AUTH_TOKEN`, `OPENAI_API_KEY`, `COPILOT_TOKEN` are dropped** from the spawned bash env. Worker file IO (`read`/`write`/`edit`) caps at 10 MiB matching `MAX_STDOUT_BYTES` in `src/lib/code-search.ts`. Path denylist for the worker's internal `read`/`glob`/`grep`/`code_search` tools (these keep their internal names — distinct from the MCP-facing rename): `.env*`, `*.pem`, `id_rsa*`, `id_ed25519*`, `.git/` interior, `.ssh/`, `.gnupg/`, `.npmrc`, `.netrc`. Full architecture + per-cap table in [`docs/peer-mcp-design.md`](docs/peer-mcp-design.md) "Worker tools".

`/mcp` also exposes the **`stand_in` tool** — a server-side, code-driven 3-lab consensus advisor for **decision tiebreak when the user is away** (`src/lib/stand-in.ts`). Polls gpt-5.6-sol xhigh (falling back to gpt-5.5) + claude-opus-5 xhigh + gemini-3.1-pro-preview high across **blind round 1 → informed round 2 → abstain**, returns a ranked-choice verdict (`consensus` / `majority` / `no_consensus` / `need_more_info`). `context` is **required** (the panel is cold-start — no repo/transcript/memory, it sees only `decision + options + context`). Beyond picking a provided option, a model may (hard-gated) propose a concrete **unlisted alternative**, surfaced in `notes` and never entering the tally (null-equivalent — it can neither form nor suppress a provided-option majority); a hallucinated/unlisted `choice` id is a parse failure (retried once, then a `VoteFailure` — never tallied as a phantom vote); and `need_more_info` fires when **≥2 of 3** parsed votes abstain citing a missing-context gap, checked in **both** round 1 and round 2 (a null-vote populates at most one escape channel — a gap takes precedence over an alternative). Scope-bound to **advisor, not decider**: recommends, never executes; dangerous actions (push, delete, drop, deploy) still require the user even with three-lab consensus. Gate (`capability: "stand_in"` → `standInToolEnabled()`): drops from `tools/list` AND fails `tools/call` with -32601 when the OpenAI slot cannot resolve to `gpt-5.6-sol` or `gpt-5.5`, or either other required model is missing from the live catalog. Slot accounting: **one slot per `stand_in` invocation, NOT one per internal model call** — the MCP boundary acquires the slot; `dispatchModelCall` (extracted from `callPersona` so non-persona callers can reuse the per-endpoint dispatch) does NOT re-acquire. A single `stand_in` call making 6 internal upstream fetches consumes exactly 1 slot from the cap=128 budget (`MAX_INFLIGHT_TOOLS_CALL`, `src/lib/mcp-inflight.ts`). `predictedTooLong` cap = 32KB on `decision + options + context` (JSON-path only; SSE bypasses; the preflight sizes only a string context — a non-string/missing context fast-fails at the tool boundary with `isError`) — fires BEFORE slot acquisition per the load-bearing invariant. **Three non-negotiables when touching the orchestrator**: (1) the protocol is code-driven, NOT model-driven — the abstain invariant and blind-R1 anti-sycophancy property must hold deterministically, not "if an orchestrator model honors them"; (2) `isError` stays `false` for `no_consensus` / `need_more_info` — those are valid protocol outcomes, not errors (`isError: true` is reserved for input-shape failures); (3) per-model effort is FIXED (not caller-tunable) — exposing knobs would invite callers to cheap out and muddy the consensus signal. Full design + verdict semantics + sibling-tool distinctions in [`docs/peer-mcp-design.md`](docs/peer-mcp-design.md) "stand_in tool (away-mode advisor)".

### First-mate cloud-agent controller (`--agents`)

`--agents` (or `GH_ROUTER_ENABLE_AGENTS=1`) adds the `first-mate` scoped MCP server (`mcp__first-mate__start_mission`, `__advance`, `__board`, plus `__mission_status`, `__scaffold_repo`, and PR operator tools including `__mark_ready`) only when `agentToolsEnabled()` also sees the second GitHub write token. The model-facing loop is thin: Claude starts missions, wakes `advance()`, answers compact `needsModel` requests, and relays human choices; the deterministic controller in `src/lib/first-mate/controller.ts` owns GitHub observation, state transitions, dispatch, retries, verifier intent, and merge mechanics. Tier1 offload is default-on but conservative: `author_fix`, `answer_agent_question`, and `decompose` can auto-answer only when high-confidence, known, low-stakes, valid-shaped, and (for decompose) dependency-verified; plan, judge, and merge-authorizing decisions always escalate to the best-model/human path. `GH_ROUTER_FM_SHADOW=0` and `GH_ROUTER_FM_TIER1_LIVE=0` opt out. Operator mode steers product implementation to GitHub cloud agents through the banner and `/gh-first-mate` skill. The reduced PreToolUse guard keeps local `mcp__workers__*` / `mcp__orchestrate__*` calls subagent-only for the main operator; file writes and Bash are not blocked. `scaffold_repo` is the foundation-first tool: it always works through a scaffold branch + PR, detects the target repo's stack/commands/tests/CI/default branch/primary OS where possible, seeds guidance + mirrored role agents + ADR/changelog/learnings/history/plans/research/PR/test/CI files, supports `add-missing-only`/`enhance`/`overwrite-approved`, reports each file as seeded/skipped/enhanced, and deliberately does not seed factory-protocol or `docs/factory/` files because first-mate remains the external orchestrator. **`scaffold_repo` is deny-by-default:** before any GitHub call, `assertScaffoldRepoAllowed()` requires its free-form `owner/name` input to match `GH_ROUTER_FM_SCAFFOLD_REPOS`; unset denies every repository. Configure a comma-separated, case-insensitive list of exact `owner/name` entries, or `owner/*` to permit an entire organization. This is a mandatory operator allowlist, not model-facing guidance: the tool creates branches, commits files, and opens PRs, and `--browse` can relay untrusted web content to a model holding that tool. Auth is dual-token: the normal Copilot App token remains untouched, while `setupGitHubAgentToken()` mints/stores `PATHS.GITHUB_AGENT_TOKEN_PATH` (`repo workflow read:org`) for the `src/lib/agent/` service layer. State is durable under `PATHS.FIRST_MATE_DIR` (`missions.json`, per-repo ledgers, decisions/approvals, packet HTML) and rehydrates via `loadAllUnits()`, so restarts/compaction/clear don't erase the board. Decomposed missions auto-complete when no live units remain, so terminal-ledger pruning cannot resurrect stale decompose requests. Merge is human-gated: approval is recorded in `decisions.json`, bound to the live PR head/base, single-use, and re-validated by `verifyAndConsumeApproval()` immediately before `mergePullRequest()`. ### Spawned-CLI auth isolation

`STRIPPED_PARENT_ENV_KEYS` (`src/lib/launch.ts`) sanitizes auth-related keys from the parent env BEFORE the proxy's overrides are merged in — prevents shell-exported credential leaks AND silences Claude Code's `Auth conflict` warnings. `getClaudeCodeEnvVars` sets `CLAUDE_CONFIG_DIR` to a router-owned mirror dir; `ensureClaudeConfigMirror` (`src/lib/paths.ts`) classifies each `~/.claude/` entry as **ISOLATED** (skipped — `.credentials.json`, lock files, `statsig/`, `cache/`, `paste-cache/`), **SHARED** (directory symlink, atomic temp+rename — `projects/`, `sessions/`, `tasks/`, `todos/`, `transcripts/`, `shell-snapshots/`, `plans/`, `file-history/`, `backups/`), or **MIRRORED** (snapshot copy — everything else). Two non-negotiable rules: **never symlink individual files** (Node's `fs.rename()` doesn't follow symlinks; Claude Code's atomic-write pattern severs them — gemini-critic finding) and **`agents/` MUST stay MIRRORED** (the proxy writes per-launch `peer-<pid>-<rand>-<name>.md` files there; a symlink would route writes/deletes into the user's real `~/.claude/agents/` and destroy custom subagent files — pinned by a `policyFor("agents") === "MIRRORED"` regression test). `sweepStalePeerAgentMdFiles` is scoped to the MIRROR only for the same reason: it reaps on filename shape plus PID liveness, and neither proves ownership, so a false positive must only ever cost a snapshot the next launch regenerates. Orphan `peer-*.md` files that a pre-mirror release left in the user's real `~/.claude/agents/` are handled non-destructively instead — `mirrorDirRecursive` SKIPS them at the copy step so they never register alongside the current launch's files under the same frontmatter `name:` (which is what made Claude Code resolve between a live and a dead definition nondeterministically). Nothing is deleted from the user's directory. The proxy then writes a synthetic `claudeAiOauth` credential to the mirror so spawned teammates (whose env-allowlist drops `ANTHROPIC_AUTH_TOKEN`) can authenticate by reading the file, AND merges `hasCompletedOnboarding: true` + `bypassPermissionsModeAccepted: true` + a synthetic `oauthAccount` into the mirrored `.claude.json` (`injectSyntheticClaudeJsonFields`) — without this, fresh machines with no prior Claude Code state hit Claude Code's first-launch wizard including the "Sign in to your Anthropic account" OAuth step, which silently defeats the synthetic credential. **Source priority for the merge** is the canonical `~/.claude.json` HOME-level path (per binary resolver `qG`: `path.join(process.env.CLAUDE_CONFIG_DIR || homedir(), ".claude.json")`) → mirror file → `~/.claude/.claude.json` subdir-level (legacy) — the mirror walk can never see the HOME-level file, so this priority is what preserves user-scope MCPs added via `claude mcp add` on default-config users. An `assertOnboardingGateInjected` postcondition re-reads the mirror file and throws if the gate fields didn't land, converting every "warn and return" branch in the helper into a launch-failing error so the OAuth wizard cannot silently re-emerge. **Do NOT re-introduce `ANTHROPIC_AUTH_TOKEN=<anything>` to the spawned-child env — historical agent-teams silent-mailbox bug; teammates drop the token from spawn allowlist and land at "Not logged in".** Full mirror policy, synthetic-credential schema (verbatim from binary `guH`), `.claude.json` onboarding-gate field rationale + source-priority logic, keychain isolation, no-401 invariant (`forwardError` 401→503 remap), and migration-from-older-versions warning in [`docs/auth-isolation.md`](docs/auth-isolation.md).

### GitHub credential lifecycle (self-healing)

The GitHub credential is **non-expiring** — verified against the live app (`has_expires_on: false`; no `github-authentication-token-expiration` header), so GitHub never issues `expires_in`/`refresh_token` and no refresh grant exists or is needed (neither the Copilot CLI, the language server, nor VS Code Copilot Chat implements one). A credential that stops working was **revoked**, not expired. Managed in `src/lib/token.ts` + `src/services/github/get-copilot-token.ts`. Five load-bearing properties, each pinned by tests in `tests/credential-recovery.test.ts`:

1. **Disk re-read on every exchange AND on a 401**, so an out-of-band `github-router auth` heals a RUNNING proxy (previously `state.githubToken` was read once at startup, which made a rejected credential a restart-only recovery). A credential the process has not tried **bypasses the refresh cooldowns** — that window is exactly the post-`auth` recovery path. A disk credential is passed to the exchange as a *candidate* (`getCopilotToken(credentialOverride)`) and published to `state` only after it succeeds: `state` is shared by every concurrent request, so an unvalidated credential visible there would be sent by unrelated in-flight requests and 401 them. Every read failure (`EPERM`/`EBUSY`/`EACCES`/`ENOENT` — routine on Windows when a read races the temp+rename write) resolves to "keep what is in memory", never to clearing it; the startup read additionally retries those codes so a launch racing an `auth` rewrite does not fail. `state.githubTokenSource === "explicit"` (an operator `--github-token`/`GH_TOKEN`) is exempt from all of this.
2. **`state.copilotTokenGeneration` is the retry criterion** in `tryRefreshAndRetry` — NOT the refresh's verdict and NOT a token-string comparison. By verdict is wrong because with A and B both holding a stale token, A can refresh while B's 401 lands inside the 30 s success cooldown and reports "skipped", failing B even though a good token is in state. By string is wrong because upstream demonstrably returns a byte-identical token from two consecutive successful exchanges. When the generation has NOT moved, the retry is skipped — a re-send would buy a second guaranteed 401.
3. **The refresh deadline is derived from `refresh_in` (a duration), never `expires_at` (an absolute timestamp)** — a clock running ahead of GitHub's would mark a brand-new token already expired and drive a refresh storm. `refresh_in` is clamped to [60 s, 6 h] AND the deadline is floored 30 s into the future: the 120 s skew exceeds the 60 s `refresh_in` floor, so a short upstream value would otherwise land in the past and spin the scheduler at 1 Hz. `ensureFreshCopilotToken()` runs on EVERY request (one integer compare on the common path; refreshes are single-flighted so they do not get more frequent — sampling was rejected because an idle-then-resumed session may never reach an "every Nth" threshold).
4. **One self-re-arming `setTimeout`**, not a fixed `setInterval` plus a separate retry timer: the delay tracks each response's own `refresh_in`, and a failure backs off (5 s → 15 s → 60 s → 300 s) instead of waiting a full period during which the token is already dead. The `disposed` flag is re-checked after every `await` — an exchange in flight at disposal would otherwise re-arm a stopped timer (pinned by `tests/fixtures/token-dispose-race-probe.ts`, which detects the leak by counting post-disposal upstream calls; an exit-based probe cannot see it, because the re-armed timer is `unref()`d). **The `inflightRefresh` guard and its assignment must never be separated by an `await`** — anything awaited between them yields the event loop and lets a second caller past the guard, so the cooldown check (which reads disk) lives INSIDE the single-flight body, and the releasing `finally` identity-checks its own promise.
5. **Failures are diagnosable and narrowly classified.** Status + redacted body + a SHA-256 credential fingerprint (8 hex, never the credential) are logged; the fingerprint is what distinguishes "process holds a stale credential" from "the credential on disk is dead". Only a `401`, or a `403` naming an entitlement problem (`access_revoked`/`subscription_ended`/`no_copilot_access`), is a rejected credential — **a bare 403 is TRANSIENT**, because GitHub returns 403 for rate limits and treating those as terminal would tell a user with a valid credential to re-authenticate.

Full rationale + the 2026-08-08 incident timeline in [`docs/auth-isolation.md`](docs/auth-isolation.md).

### Browser-control MCP (`--browse`)

`github-router start --browse` (or `claude --browse` / `codex --browse`, or `GH_ROUTER_ENABLE_BROWSE=1`) opt-in flag adds 19 browser-control tools under the `browser` MCP server (`mcp__browser__*`) to the `/mcp` surface, letting the model drive a real Chrome / Edge browser through an MV3 extension shipped under `src/browser-ext/`. The capability gate `browserToolsEnabled()` (in `src/lib/mcp-capabilities.ts`, also consulted by `claude.ts` to decide whether to register the `browser` server) requires BOTH the opt-in AND a positive `hasSupportedBrowserInstalled()` check, mirroring the symmetric list-time + call-time pattern used by `workerToolsEnabled()` and `standInToolEnabled()`. MCP-facing tool names (prefix dropped): `list_tabs / open_tab / close_tab / navigate / read_page / scroll / screenshot / keyboard / wait / eval_js / download / mouse / drag / type / diagnostics / find / act / observe / extract`. **The rename is MCP-facing only** — the wire `tool` string the extension dispatches on stays `browser_*` (unchanged in `src/lib/browser-mcp/index.ts`), so installed extensions need no reload. Element refs returned by `read_page` are the primary input to subsequent act / mouse / drag calls — preferred over CSS selectors because refs survive dynamic class names. The humanlike-input set (`mouse / drag / type`) routes through CDP `Input.dispatchMouseEvent` / `dispatchKeyEvent` for trusted events, hover-to-reveal menus, drag-and-drop (auto-detects HTML5-DnD via `Input.setInterceptDrags` + `Input.dispatchDragEvent` when source has `draggable="true"`), and per-keystroke typing. Three load-bearing invariants: (1) every action takes an explicit target — no stateful cursor cache (MV3 SW dormancy would wipe it silently); (2) `withTabInputLock(tabId, fn)` serialises mouse / drag / type / keyboard / scroll(at-pointer) per tab (CDP mouse state is global per attachment); (3) pre-click `elementFromPoint` hit-test fails with `target_obscured` if an overlay covers the target, bypass via `force: true`.

Every tool runs an implicit pre-flight (`ensureBridgeReady()` in `src/lib/browser-mcp/install-check.ts`) BEFORE acquiring an inflight slot (same load-bearing invariant as `predictedTooLong`). The pre-flight (1) auto-installs the native-messaging-host manifest for every detected browser (file write on POSIX, HKCU registry write + JSON file on Windows via `reg.exe`), and (2) probes the bridge's `<APP_DIR>/browser-mcp/bridge.json` discovery file + `/health` bearer-token-authed endpoint. On miss the dispatcher returns a structured `install_required` JSON text block with `isError: true` carrying a `load_unpacked_dir` path the user / model can act on. **Stable-dir materialization (`src/lib/browser-mcp/provision.ts`)**: because `npx`/`bunx` install into an ephemeral cache path that changes per version, the extension + bridge bundle are copied into a STABLE app-dir (`<APP_DIR>/browser-ext/` + `<APP_DIR>/browser-bridge/index.js`) on every launch — `provisionBrowserAssets()` runs fire-and-forget after `setupAndServe` (gated on the browse opt-in) AND lazily at the head of `ensureBridgeReady()`. The running `getPackageVersion()` is stamped into the materialized `manifest.json` in this one place on start, so a one-time "Load unpacked" of the stable dir survives upgrades and the version-mismatch `__reload__` picks up new code. The resolvers split: `bundledExtensionDir()`/`bundledBridgeBundlePath()` are the copy SOURCE (dist→src), while the runtime `extensionDir()`/`bridgeBundlePath()` prefer the stable copy (`GH_ROUTER_BROWSER_EXT_DIR` override wins for `extensionDir()`). Provisioning is signature-idempotent, single-flight, never throws; opt out with `GH_ROUTER_DISABLE_BROWSER_PROVISION=1` (also the lever the non-isolated gate test uses to stay hermetic). The extension's stable ID is derived deterministically from a fixed RSA pubkey in `src/browser-ext/manifest.json` `key` field via `computeExtensionIdFromKey()` (sha256-of-DER → first 16 bytes → hex-value-to-[a-p] map). The bridge bundle (materialized at `<APP_DIR>/browser-bridge/index.js`, bundled at `dist/browser-bridge/index.js`) is invoked by Chrome via a generated launcher shim that prefers `node` over `bun` (bun closes the bridge's binary stdin prematurely on SW dormancy). Navigation block is dual-layered: the bridge-side `preflightUrlPolicy()` in `src/lib/browser-mcp/policy.ts` checks `browser_open_tab` / `browser_navigate` URL args before forwarding, AND the extension's `webNavigation.onBeforeNavigate` listener cancels in-page-initiated nav (JS redirects, meta-refresh) to about:blank. `chrome://settings`, `chrome://extensions`, `chrome://flags`, password / management / policy pages, and `chrome-extension://*/options.html` blocked; `devtools://*` explicitly allowed. Opt-in audit log via `GH_ROUTER_LOG_BROWSER_MCP=1` (mirrors `GH_ROUTER_LOG_PEER_MCP` convention). Full architecture, install flow, per-OS NMH paths, MV3 SW dormancy + bridge grace-window handling, and the Playwright E2E harness in [`docs/browser-mcp-design.md`](docs/browser-mcp-design.md). E2E suite is gated on `GH_ROUTER_RUN_BROWSER_E2E=1` so it doesn't clash with the rest of `bun test` (some upstream tests mock `os.homedir()` which leaks into the bridge.json path resolution).

### Thinking-mode translation

Copilot rejects Anthropic's `thinking:{type:"enabled", budget_tokens:N}` shape on adaptive-thinking models with HTTP 400. The router translates to Copilot's `thinking:{type:"adaptive"}` + `output_config:{effort}` automatically when the resolved model declares `adaptive_thinking: true`. Bucket: `<2k → low`, `<8k → medium`, `<24k → high`, else `xhigh`. `EFFORT_ORDER` is `["none","low","medium","high","xhigh","max"]` — both ends are reachable only by an explicit `output_config.effort`, never by bucketing, because an unbounded `budget_tokens` cannot safely infer a `max` threshold. Listing `none` (advertised by every gpt-5.x catalog entry) is load-bearing: while it was missing, a client asking for the MINIMUM on a model that lacks it counted as unrecognized and clamped to `high`, the maximum. An effort that is genuinely unrecognized anchors at `UNKNOWN_EFFORT_ANCHOR` (`xhigh`, deliberately NOT the top of the ladder) and clamps down, so a guess never resolves to the priciest tier a model offers. Clamps to `model.capabilities.supports.reasoning_effort` allowlist when present (lower-tier preference for ties). Client-supplied `output_config.effort` always wins. The non-Claude translation shim applies that same precedence before its thinking-budget or absent-thinking-default branches. No-op when the model lacks `adaptive_thinking` (passthrough). Implemented in `src/routes/messages/handler.ts` (`translateThinking`).

### Anthropic-translation shim (non-Claude models on `/v1/messages`)

`github-router claude`'s MAIN agent loop can run on non-Claude Copilot models. Copilot serves Claude models on its native `/v1/messages`, but a gpt/gemini request there 400s, and Claude Code speaks only the Anthropic Messages wire format — so a shim (`src/lib/anthropic-translate/`) translates Anthropic Messages ⇄ Copilot's `/responses` (gpt-5.6-sol, gpt-5.5, gpt-5.3-codex) and `/chat/completions` (gemini-3.5-flash, gemini-3.1-pro-preview) shapes, streaming and non-streaming. The `/v1/messages` handler (`src/routes/messages/handler.ts` ~L296-336) computes the route once via `classifyMessagesRoute`: Claude models (keyed off identity — vendor/family/`CLAUDE_ID_RE`, fail-CLOSED so a Claude alias is never diverted) fall through to the EXISTING `createMessages` passthrough byte-for-byte unchanged; a non-Claude model routes to the shim by its catalog `supported_endpoints` (never a hardcoded slug list). Both shim paths share ONE provider-neutral IR (`src/services/copilot/responses-request.ts`, `assembleResponsesPayload` — also fed by the worker-agent stream, so the two can't drift) parsed by `parseAnthropicRequest`; only wire assembly differs. Assistant `thinking` blocks are dropped (not replayable); explicit `output_config.effort` has highest precedence, then `thinking.budget_tokens` buckets+clamps to `reasoning.effort`, then an absent `thinking` field defaults to `high` (clamped to the model's allowlist — gemini has no xhigh so it lands on `high`). This preserves the effort picker for non-Claude models: it wins alone, over a thinking budget, and alongside `thinking:{type:"adaptive"}`; explicit `thinking` without an effort remains its own signal. `stop_sequences`→`stop` (best-effort: accepted on both endpoints without 400; honoring is upstream-dependent — accepted-but-silently-ignored on `/responses`/gpt (a Copilot Responses-API limitation), not conclusively verified on `/chat/completions`/gemini; low-impact, Claude Code rarely sends it) and `tool_choice.disable_parallel_tool_use:true`→`parallel_tool_calls:false` are forwarded to both endpoints (accepted without 400, live-verified HTTP 200; omitted-by-default so the worker payload is byte-identical). **C1 streaming correctness**: tool-call args are BUFFERED per stable stream key (`/responses` `output_index`, NEVER the re-encrypted `item_id`; chat `tool_calls[].index`) and each tool block is emitted ATOMICALLY (start → one `input_json_delta` with the full assembled args → stop) at that tool's own terminal (`output_item.done` for Responses, end-of-stream for chat) at a distinct block index — because Copilot emits all parallel-tool `output_item.added` events before the first args delta, so opening at `added` time would ship empty args and drop the deltas (the parallel-tool-args-lost bug). A stream that ends without its terminal marker (`completed`/`incomplete`/`failed`, or `[DONE]` on chat) throws → terminal Anthropic `event: error`. The synthesized SSE goes out through `anthropic-sse.ts`'s pull-based `ReadableStream` adapter under the repo's stream-lifecycle mandate (guards enqueue/close against the consumer-cancel race, caller-owned `AbortController` never `c.req.raw.signal`). Egress relies on Copilot emitting stream items sequentially (only the parallel-tool `added` burst batches); if that contract were ever violated a text-tail or reasoning `signature_delta` could be silently lost (two labs confirmed it's contract-gated and doesn't occur today; Phase 5 live E2E is the empirical backstop). **Model gaps** (inherent, not shim bugs): gemini has no `xhigh` (clamps to `high`) and no `structured_outputs`; gpt-5.3-codex is 400k context; there's no `-1m` variant to pick — 1M is native on the base slug for gpt-5.6-sol, gpt-5.5, and gemini. **Phase 3 native selection** (`src/lib/server-setup.ts`): the five models become selectable `/model` picker rows by pre-seeding Claude Code's gateway-model discovery cache (`<CLAUDE_CONFIG_DIR>/cache/gateway-models.json`, atomic temp+rename) with the catalog-present subset and conditionally enabling `CLAUDE_CODE_ENABLE_GATEWAY_MODEL_DISCOVERY`. The row `id` receives `[1m]` only when its exact catalog entry advertises at least 1M context and `CLAUDE_CODE_DISABLE_1M_CONTEXT` is unset; display labels stay bare. Thus gpt-5.6-sol, gpt-5.5, and the two Gemini rows receive the local 1M accounting unlock, while 400k gpt-5.3-codex stays bare. The cache-READ path has no id filter and APPENDS, so the opus/sonnet/haiku tiers are untouched and the hazardous network-fetch path stays blocked. Explicit `-m <id>` selection also routes through the shim regardless of the picker. ADVISOR + a non-Claude model gracefully degrades: the handler strips the injected `__anthropic_advisor` tool + advisor beta and routes to the shim (per-request, so it survives a runtime `/model` switch) — the server-side advisor loop is Claude-only, so it's simply unavailable on a translated model; it does NOT 400, so `github-router claude -m gpt-5.5` works out-of-the-box (the auto-enabled advisor tool no longer breaks non-Claude models). Full design in [`docs/anthropic-translation-shim.md`](docs/anthropic-translation-shim.md).

### Semantic code search (folded into the `code` tool, ON by default)

ColBERT/PLAID semantic search is the **default mode of the unified `mcp__search__code` tool** (`mode: "semantic"`), backed by the router-managed [`colgrep`](https://github.com/lightonai/next-plaid) sidecar (`src/lib/colbert/`). There is no longer a standalone `semantic_search` tool. The routing lives in `src/lib/unified-code-search.ts` (`runUnifiedCodeSearch`), shared by both the MCP `code` tool and the worker subagent's internal `code_search` tool. **On by default** (opt OUT with `GH_ROUTER_DISABLE_SEMANTIC_SEARCH=1`): `start`/`claude`/`codex` fire-and-forget `provisionAndIndexColbert()` after `setupAndServe` (mirroring `provisionToolbelt()`), which SHA-pins-and-downloads three artifacts (the colgrep binary + ONNX Runtime CPU dylib + ColBERT INT8 model) into `~/.local/share/github-router/colbert/`, runs a **post-provision smoke test** (load-bearing — an invalid `ORT_DYLIB_PATH` makes colgrep silently fall through to its OWN unverified GitHub download; the smoke test scans stderr for colgrep's "not a loadable ONNX Runtime dylib; ignoring" warning and fails the handoff), then background-indexes the cwd if it's a git repo. **Transparent fallback (the merged-tool contract):** when colgrep isn't attemptable (artifacts absent / opted out) or the per-workspace index is `building`/`stale`/`unavailable`/`failed`, the `code` tool's semantic mode FALLS BACK to lexical BM25F and labels the response with a 3-valued `source` (`semantic` | `lexical` | `lexical-fallback`) so a degrade is never silent; semantic-ready rows additionally carry a ColBERT `score`. **Contract split (load-bearing):** `runSemanticSearch` in `src/lib/colbert/runner.ts` is UNCHANGED and still has its strict NO-LEXICAL-FALLBACK contract (honest `status`, never another engine); the fallback lives ONLY in the `unified-code-search.ts` tool layer. The availability predicate is the leaf `colbertSearchEnabled()` in `src/lib/colbert/` (single source of truth: `(NOT opted-out) AND colbertArtifactsPresent() AND colbertSmokeOk()`); `semanticSearchEnabled()` in `src/lib/mcp-capabilities.ts` delegates to it and no longer gates a tool's `tools/list` visibility — the `code` tool is ALWAYS listed (it always returns results via fallback), so the `search` group stays `{code, web}` regardless of colgrep availability (the **zero-regression guard**: on CI / sandboxes / pre-provision, colgrep is absent ⇒ semantic mode falls back to lexical, the surface is unchanged). The git **freshness verdict** (`src/lib/colbert/index-store.ts`) is the staleness correctness guard: a query is `fresh` only when `git rev-parse HEAD` matches the last index AND the tree isn't newly dirty — a branch switch or file deletion flips it to `stale` so a possibly-deleted-symbol hit is never labeled `ready`. colgrep is CLI-per-invocation (no daemon): a search NEVER kills colgrep mid-write — colgrep auto-indexes/reconciles during a search when its index is behind (no read-only flag), and killing that mid-write orphans index docs → a DB↔index desync that every later search re-triggers (the original corruption bug). So a search runs colgrep under the build-grade watchdog (reaps only a truly hung child — no output AND no index-dir growth for `INIT_STALL_MS`; `INIT_TIMEOUT_MS` is a runaway backstop) with the byte cap set to TRUNCATE-not-kill (a huge result must not tree-kill non-atomic colgrep), and the CALLER never waits that long: if results aren't back within `GH_ROUTER_COLBERT_SEARCH_RESPOND_MS` (default 20s) the search DETACHES — returns a `building` fallback and lets the colgrep child finish indexing in the background (tracked, never mid-write-killed) so the next query is fast; a per-workspace lock (held from spawn until the colgrep child exits) serializes searches so two can't reconcile as unsynchronized writers — a sequential pattern never contends, only a simultaneous same-workspace batch (losers get a lexical fallback + retry). (A warm search is sub-second → `semantic`.) Plus stdout byte cap + tree-kill (POSIX process-group / Windows `taskkill /T`), an in-memory PID ledger reaped on SIGINT/SIGTERM/exit, and a boot-time sweep that reclassifies dead-`buildPid` `building` entries to `failed`+`failureClass:"crashed"` (never killing a recycled PID from a prior boot). **Index BUILD state is detected from real signals, not guessed from a fixed timeout** (a blunt timeout can't tell a legit multi-hour 50GB build from a hung one): the background build runs under a STALL watchdog (`runManagedExeCapture` `inactivityTimeoutMs` + an `indexDirSignature` disk-growth probe — colgrep is SILENT on a non-TTY pipe during the encode, so disk growth, not output, is the progress signal) that lets a progressing build run to completion and kills only a frozen one (`GH_ROUTER_COLBERT_INIT_STALL_MS`, default 5min; absolute runaway backstop `GH_ROUTER_COLBERT_INIT_TIMEOUT_MS`, default 6h). The per-query freshness verdict mirrors the boot sweep's `isPidAlive` check (`verdict:"crashed"`) so a MID-SESSION proxy-kill/OOM crash is caught + self-heals on the next query, not only at the next boot; a failed build records a `failureClass` (`crashed`/`stuck`/`error`/`launch`) + a `failedAttempts` counter (reset on success), and the runner re-kicks a debounced re-index under a per-class cap (stuck once, transient ≤3) + a 5min backoff, going operator-actionable past the cap — `failed` is no longer a session-terminal dead-end, and `provisionAndIndexColbert`'s startup auto-kick skips a capped/`stuck` workspace so a restart loop can't re-burn a known-bad build. The `lexical-fallback` notice is INSTRUCTIVE (retry `mode:"semantic"` shortly while the index self-heals, or re-query with specific symbols); the lexical backend (`code-search.ts`) is deliberately NOT tokenized for NL phrases — the model is steered to the right lever, not fed noisy OR-matches. The managed binary is a native `.exe`, NOT a `.cmd` shim, so it bypasses `buildExecInvocation`'s cmd.exe path (which throws on `%`) via `runManagedExeCapture` (`src/lib/exec.ts`, `shell:false` everywhere — `%`/`&`-in-workspace-path safe). Re-pin SHAs with `bun run scripts/gen-colbert-manifest.ts`. Full design + adversarial-review record in [`docs/semantic-search.md`](docs/semantic-search.md) + [`docs/research/colbert-sidecar-design.md`](docs/research/colbert-sidecar-design.md).

### Runaway tool-loop guard

`src/lib/tool-loop-guard.ts` bounds a client-side agent that has wedged on one tool call. Motivating incident: a backgrounded `reviewer` subagent repeated one identical `Read` **4,020 times over 11h39m** — 4,060 billable turns, 1.536B input tokens, 203K output tokens and no final answer (every turn stopped on `stop_reason: "tool_use"`, so the review never returned) — and stopped only when the user interrupted it. Claude Code's duplicate-read guard had replaced the file content with `"Wasted call — file unchanged since your last Read. Refer to that earlier tool_result instead."`, which counts no repeats and never aborts, so it became a fixed point. The repo's existing `DEFAULT_MAX_REPEATED_CALLS = 3` (`src/lib/worker-agent/budget.ts:50`) governs only in-process Pi workers; native Claude Code subagents reach the proxy purely as HTTP requests.

**Two tiers, one pair of thresholds.** `GH_ROUTER_LOOP_NUDGE_AT` (default 4) injects a corrective sibling block; `GH_ROUTER_LOOP_ABORT_AT` (default 7) rejects the request. `0` disables a stage; parsed by a local strict `envThreshold` (digits-only, warns) that differs from `port.ts`'s `envInt` in ACCEPTING `0`, because `0` is meaningful here. **Tier A** matches results that are exactly a known client redundancy marker (`CLIENT_REDUNDANCY_MARKERS`) — the client has already adjudicated the call redundant, so no silence test is needed. **Tier B** is the generic backstop and additionally requires the whole run to be SILENT (no text/thinking) before aborting, because identical results do NOT distinguish a poll (`{"status":"queued"}` is byte-identical for minutes) from a wedged model — narration does.

**Three non-negotiables.** (1) Comparison is **per-TURN**, not per-call: flattening a parallel-tool turn yields `A,B,A,B` where no two neighbours match, so a repeating parallel batch never registers, and it makes seven calls inside ONE turn look like a run of seven when zero feedback cycles have completed. Calls are paired to results **by tool-call id**, then sorted, so serialization order cannot change the verdict. A tool-less assistant turn is emitted with no calls so it BREAKS the run — dropping it would splice the tool turns either side into a false "consecutive and silent" run and abort an agent that was visibly reasoning. (2) Tier A matches **whole-result equality, never substring** — the marker text lives in this repo's docs and in stored transcripts, so substring matching would fire on an agent reading its own project. (3) **Detection is read-only and never re-serializes.** A nudge necessarily does, since injection requires it; that is the same round-trip `resolveModelInBody` already performs whenever it modified the body (`modified ? JSON.stringify(parsed) : rawBody`), which for Claude Code is the norm because the model slug is rewritten. So a nudge does not add a new class of hazard, but it does extend the existing large-integer round-trip exposure (`9007199254740993` → `…992`) to the rare request that would otherwise have passed through raw. Detection alone never triggers it.

Nudges are injected as a **protocol-valid sibling** (an extra Anthropic `text` block / OpenAI `user` message / Responses input item), never appended into a result payload — `{"status":"ok"}` plus a sentence is no longer valid JSON. Siblings go at the tail so the prompt-cache prefix survives.

Wired at three sites: `src/routes/messages/handler.ts` (before the `classifyMessagesRoute` fork, so one site covers Claude passthrough AND both shims), `src/routes/chat-completions/handler.ts`, `src/routes/responses/handler.ts`. Abort envelopes are **format-specific** (Anthropic `{type:"error",...}` vs OpenAI `{error:{...}}`) and carry **`x-should-retry: false`**. That header is load-bearing, not decoration: the proxy cannot kill a client's agent loop, only refuse, so a refusal the client retries would trade a tool loop for a retry loop. Claude Code's `shouldRetry` (verified in the installed 2.1.226 bundle) retries 401-with-token-cache, 408, 409, 429, and `>= 500`, so a bare `400` is already terminal — but it consults `x-should-retry` BEFORE any status test, so sending it explicitly survives a future change to that list. **`/v1/responses/compact` and `/v1/messages/count_tokens` are deliberately NOT guarded** — compact is the client's own escape from a runaway history, and count_tokens triggers no inference. Known false negatives, documented not papered over: a cycle whose period exceeds one turn (turn A, turn B, turn A), a client that truncates history to a sliding window, and Responses clients using `previous_response_id`. `tests/canaries/client-loop-markers.test.ts` pins the markers against the installed Claude Code build (searching both the raw string and its `\uXXXX`-escaped bundle form) so a client reword fails on any machine that has the client. It SKIPS where no install is present, which includes CI — absence there proves nothing, so marker drift is caught on developer and operator machines rather than in the CI matrix.
